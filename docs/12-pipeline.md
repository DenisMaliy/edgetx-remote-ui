# Повний шлях даних

Довідник по всьому конвеєру (pipeline) — від кадру, намальованого EdgeTX
усередині пульта, до пікселів у вікні браузера, і від дотику пальця до
телефона назад до події вводу в EdgeTX.

Документ описує **поточний стан**, а не історію. Числа взято з коду й із
розділів «Результат» задач; там, де числа немає або воно не міряне, так і
написано — **«не міряно»**.

## Як читати цей документ

Скрізь, де можливо, наводяться **два** числа:

- **стеля** — межа, поставлена залізом, буфером або константою в коді;
- **фактично** — заміряне на живому стенді значення під названим
  навантаженням.

Приклад: канал AUX1 на 2 625 000 бод тримає 262 500 Б/с (**стеля**), а під
гортанням меню через нього йде 154–172 КБ/с, тобто 60–67 % (**фактично**).

⚠️ **Головний висновок усього документа:** вузьке місце конвеєра **переїжджало
тричі**. Спершу ним був дріт на 921600 бод (90 % завантаження), потім —
пам'ять моста, тепер — **швидкість малювання самого EdgeTX на STM32F429**.
Дріт на 2 625 000 завантажений на 16–21 % під протягом пальцем.

Позначки в тексті:

- ⚠️ — місце, де щось може не встигнути або де дані свідомо викидаються;
- ⛔ — питання закрите заміром, повертатись не варто.

## Загальна схема

```
┌───────────────────────── TX16S · STM32F429 · 168 МГц ─────────────────────────┐
│                                                                              │
│  LVGL малює                                                                  │
│      │                                                                       │
│      ▼  flushLcd()  ← гачок remoteUiOnFlush(x1,y1,x2,y2,pixels,isLast)       │
│  ┌──────────────────────────────────────────┐   задача menusTask, пріоритет 1│
│  │ memcpy зміненого прямокутника             │   (мікшер витісняє будь-коли) │
│  │ у тіньовий кадр 261 120 Б  (SDRAM)        │                               │
│  │ + біти «брудна» в карті 135 плиток (20 Б) │                               │
│  └──────────────────────────────────────────┘                               │
│      │                                                                       │
│      │ бітова карта, без м'ютекса (release / acquire)                        │
│      ▼                                                                       │
│  ┌──────────────────────────────────────────┐   ВЛАСНА задача FreeRTOS       │

│  │ → буфер передачі 4103 Б у .ram (__DMA)   │   нікого не чекає              │
│  └──────────────────────────────────────────┘                               │
│      │                                                                       │
└──────┼───────────────────────────────────────────────────────────────────────┘
       │  AUX1 = USART3 + DMA1 Stream3 Ch4,  3.3 В, без керування потоком
       │  921600 бод (домашня) … 2 625 000 бод (стеля = PCLK1/16)
       ▼
┌───────────────────────── ESP32 DevKit v1 (WROOM-32) ─────────────────────────┐
│                                                                              │
│  UART1 GPIO16/17 → буфер драйвера 48 КіБ  ─►  rx_task (пріоритет 12, ядро 1) │
│                                                 │ розбір кадрів (маркер+CRC) │
│                                                 ▼                            │
│                                    накопичувач пачок 8192 Б                  │
│                                                 │ (FRAME_END віддається одразу)│
│                                                 ▼                            │
│                                    кільцева черга 24 КіБ ─► ws_tx_task (6)   │
│                                                                 │            │
│  httpd (пріоритет 5, ядро 0): сторінка + /api/stats + /ws       │            │
│  Wi-Fi AP, канал 6, 8.5 дБм, WPA2, 192.168.4.1 ◄────────────────┘            │
└──────────────────────────────────────────────┬───────────────────────────────┘
                                               │ WebSocket, двійкові кадри
                                               ▼
┌───────────────────────────── Браузер (телефон / ПК) ─────────────────────────┐
│  розбір кадрів → TILE → RLE16 назад → позаекранний буфер 480×272 RGBA        │
│  показ на FRAME_END за політикою очікування (wait.js, dirtyTiles)            │
│  ввід: KEY / ENC / TOUCH / TRIM + INPUT_STATE раз на 250 мс ─────────────────►│
```

труби TCP і спільного UART.

# Частина I. Пайплайн монітора

## 1. LVGL і гачок `remoteUiOnFlush`

**Що це.** Єдина точка, з якої ми дізнаємось, що екран змінився. EdgeTX має
власний проміжний зворотний виклик між LVGL і драйвером екрана —
`lcdSetFlushCb()` у `radio/src/gui/colorlcd/lcd.h`, — і наш гачок стоїть на
самому початку `flushLcd()` (`radio/src/gui/colorlcd/lcd.cpp`), **до** блоку
раннього виходу за `lv_disp_flush_is_last()`.

Гачок займає 8 рядків у чужому файлі (`docs/05-hooks.md`, пункт 5) і приймає
лише цілі числа й вказівник — типи LVGL розбираються на місці виклику:

```cpp
remoteUiOnFlush(area->x1, area->y1, area->x2, area->y2,
                (const uint16_t*)color_p, lv_disp_flush_is_last(disp_drv));
```

Реалізація — `firmware/edgetx-patch/remote_ui/capture.cpp:302`.

**Характеристики й обмеження.**

| | |
|---|---|
| Контекст виконання | задача `menusTask` — пріоритет **1**, період циклу **50 мс**, стек 8192 Б (`radio/src/tasks.cpp:51`, `tasks.h:28,46`); мікшер витісняє її будь-коли |
| Що дозволено всередині | тільки `memcpy` у тіньовий кадр і встановлення бітів |
| Що заборонено | DMA2D, очікування, виділення пам'яті (`docs/02-architecture.md`) |
| Координати | логічні, **неповернуті**; поворот на 180° робить драйвер TX16S нижче за нашу точку |
| Розкладка пікселів | щільна, крок рядка = ширина області (непрямий режим LVGL, чинний для TX16S) |
| Обрізання по екрану | так, `capture.cpp:119-123` |
| Ознака кінця кадру | `isLast` → `s_frameCount` збільшується на 1 |

**⚠️ Стеля проти фактичного.**

- Драйвер екрана в тій самій задачі блокується на очікуванні кадру LTDC
  (`targets/horus/lcd_driver.cpp:130-134` — цикл `while (_frame_addr_reloaded)`,
  без тайм-ауту). ⚠️ Число «до ~19 мс» із `docs/02-architecture.md` **у коді
  явно не стоїть**: воно виводиться з частоти LTDC (60 Гц → ~16.6 мс на кадр),
  а не заміряне. На цьому фоні наш `memcpy` — десятки мікросекунд. Точний час
  гачка **не міряно**.
- Скільки кадрів за секунду закриває сам LVGL — заміряно опосередковано,
  лічильником моста `uart.frames`: **2.6–4.3 кадр/с** під протягом пальцем і
  **13.6 кадр/с** під енкодером (8 клацань/с) — задача 0020. У задачі 0018
  заміряно **17.1 `FRAME_END`/с**, тобто 58 мс на кадр.
- ⛔ **Це і є нинішнє вузьке місце всього конвеєра.** Пропускна здатність
  малювання приблизно стала — **150–190 наших плиток за секунду**, — а частота
  кадрів дорівнює цій здатності, поділеній на розмір кадру. Під протягом
  рухається весь список, тож кадр учетверо більший (44 плитки проти 11), і
  кадрів виходить учетверо менше. Гіпотезу «винна наша задача транспорту, бо
  вона витісняє малювання» відхилено наявними числами (задача 0020, рецензія).

**⚠️ Обмеження, чинне для інших пультів.** На цілях із прямим режимом LVGL
(T18, X12S, V16) крок рядка дорівнює `LCD_W`, а не ширині області, і чинний
код прочитав би там сміття. Рішення ухвалено (гачок отримує додатковий
параметр — крок рядка), реалізація відкладена разом із кроком 1.7.

## 2. Тіньовий кадр і бітова карта брудних плиток

**Що це.** Гачок приносить лише змінені прямокутники, а клієнту плитка
потрібна цілою — тому останній відомий вигляд екрана треба десь тримати.
`firmware/edgetx-patch/remote_ui/capture.cpp:43`.

**Характеристики й обмеження.**

| | Значення | Звідки |
|---|---|---|
| Роздільність | 480×272, RGB565 | `LCD_W`/`LCD_H` через `geometry.h` |
| Тіньовий кадр `s_shadow` | **261 120 Б**, у **SDRAM** (`__SDRAM`) | у 192 КБ внутрішньої ОЗП F429 не влізло б |
| Сторона плитки `TILE_SIDE` | **32** | `geometry.h:55` |
| Сітка | 15 × 9 = **135 плиток** | 480/32 = 15, ceil(272/32) = 9 |
| Крайні плитки | можуть бути нижчими: 272 = 8×32 + 16 | нормальний випадок, не помилка |
| Бітова карта `s_dirty` | **20 Б** (5 слів по 32 біти) | `std::atomic<uint32_t>`, без м'ютекса |
| Синхронізація | гачок: пікселі → біт (`release`); транспорт: біт → пікселі (`acquire`) | `capture.cpp:94,175` |

**Чому плитка саме 32×32.** Сира плитка разом із заголовком мусить
гарантовано влазити в один `PAYLOAD`: 32·32·2 + 9 = **2057 Б** при стелі
**4096**. Плитка 64×64 дала б 8201 Б — і різати її в момент відправлення нема
куди, бо на однорідному шумі RLE не виграє й плитка йде сирою.

**⚠️ Що тут свідомо не гарантується.**

- Карта фіксованого розміру **не переповнюється за побудовою**, тому зміна не
  губиться. Найгірше, що буває: плитка піде зшита з двох кадрів, а наступним
  проходом — цілісна.
- **Забрану** плитку, яку не вдалось відправити, транспорт зобов'язаний
  повернути (`captureReturnTile()`).
- ⚠️ Секція `.sdram` оголошена як `NOLOAD`, тобто при старті її ніхто не
  обнуляє: на пульті тіньовий кадр починає життя зі сміття від попереднього
  вмикання. Чиститься при першому ж флеші (`s_shadowReady`). До першого флешу
  `captureMarkAllDirty()` **відмовляє**, і `REFRESH` відкладається, а не зникає.

**⚠️ Стеля проти фактичного.**

- Тіньовий кадр — 261 120 Б із ~8 МБ SDRAM. Разом із власними буферами EdgeTX
  зайнято 3 665 152 Б, тобто **вільно ~4.5 МБ**.
- ⚠️ На кольоровій цілі **без** SDRAM підхід доведеться переглядати — таких
  цілей ми зараз не збираємо.
- `dirtyTiles` під навантаженням: стеля залишку **~96 зі 135**. Усі режими
  керування лежать у діапазоні **80–96** — неспішний енкодер 83, швидкий 94,
  гортання 96, перескок сторінки 89 (задача 0019). До розміру сітки не
  наближається ніколи.

## 3. Задача транспорту в пульті

**Що це.** Власна задача FreeRTOS, яка забирає брудні плитки, стискає,
кадрує й віддає драйверу. Створюється лише при переведенні AUX1 у режим
`REMOTE_UI`. `firmware/edgetx-patch/remote_ui/transport_uart.cpp`.

**Характеристики й обмеження.**

| Параметр | Значення | Рядок |
|---|---|---|
| Пріоритет | **2** = `MENUS_TASK_PRIO + 1` | `transport_uart.cpp:233` |
| Стек | 512 слів = **2 КБ**, у CCM | `:230` |
| Період проходу `POLL_PERIOD_MS` | **2 мс** | `:186` |
| Період, коли порт не наш | 20 мс | `:190` |
| Скид декодувальника за тишею | **100 мс** | `:198` |
| «Клієнта більше немає» | **3000 мс** | `:209` |
| Байтів приймання за прохід | не більше **1024**, шматками по 64 | `:754` |
| Буфер передачі `s_txBuf` | **4103 Б** у `.ram`, з `__DMA` | `:285` |

**Розклад пріоритетів FreeRTOS у пульті** (`radio/src/tasks.h:44-46`,
`FreeRTOSConfig.h`):

| Пріоритет | Задача |
|---:|---|
| 4 | **мікшер** — період 4000 мкс типово (задає протокол радіомодуля, мін. 850 мкс, макс. 50 000) |
| 3 | звук |
| **2** | службова задача таймерів (`per10ms()` раз на 10 мс, телеметрія раз на 2 мс) **і наш транспорт** |
| 1 | `menusTask` — малювання, період 50 мс |

`configMAX_PRIORITIES = 5`, `configTICK_RATE_HZ = 1000`,
`configUSE_TIME_SLICING = 1` (типове).

**Чому пріоритет 2.** Мікшер (4) і звук (3) витісняють транспорт **завжди** —
радіоканалу він зачепити не може за побудовою, а не за домовленістю. Малювання
(1) транспорт витісняє сам, тож приймання вводу не стає заручником перемальовки.
⚠️ Щабель 2 не вільний: на ньому вже сидить службова задача таймерів
(`per10ms()`, телеметрія). Затримка їй не зникає, а обмежується тактом
планувальника — рівні пріоритети діляться часом.

**⚠️ Транспорт нікого не чекає.** `waitForTxCompleted()` не викликається
жодного разу. Замість очікування — питання `txCompleted()` на початку передачі:
DMA ще жує буфер → цього проходу не передаємо нічого, плитки лишаються
брудними. Задача, що чекала б на 921600, чекала б до 45 мс на кадр — і всі ці
45 мс не працювала б `menusTask`.

**⚠️ Стеля проти фактичного.**

| | Стеля | Фактично |
|---|---|---|
| Прохід задачі | 2 мс періоду | порожній — одиниці мкс; найдорожчий (`REFRESH`, ~130 плиток у пачці) — **одиниці мілісекунд** |
| Приймальна черга драйвера | 512 Б ≈ 5.5 мс потоку на 921600 | клієнт шле ~**80 Б/с**, тобто в нормі черга майже порожня |
| Найбільша пачка | 4103 Б = **~44.5 мс** на 921600, **~15.6 мс** на 2 625 000 | приблизно один кадр перемальовки |
| Найгірший цикл мікшера `Tmix max` | період 4 або 7 мс (задає протокол радіомодуля) | **0.44–0.47 мс**, тобто 6.3–11.8 % періоду; циклів не пропущено |

⚠️ `Tmix max` знімався під потоком 80–90 КБ/с (задачі 0010, 0012, 0014) і під
**145 КБ/с** на 2 625 000 (задача 0019) — це найбільший потік, при якому число
взагалі колись знімалось.

## 4. Стиснення RLE16 і пакет `TILE`

**Що це.** Плитка стискається серіями по 16-бітних пікселях. Кодувальник
рахує обидва варіанти й бере менший — стиснення ніколи не робить гірше.
`rle16.cpp`, `tile.cpp`.

**Формат.**

```
TILE PAYLOAD:  [x:2][y:2][w:2][h:2][метод:1][дані…]
метод 0 = сирі пікселі RGB565 LE,  1 = RLE16
RLE16:  послідовність пар [лічильник:1][піксель:2],  лічильник 1…255
```

**Характеристики й обмеження.**

| | |
|---|---|
| Заголовок `TILE_HEADER_SIZE` | **9 Б** |
| Стеля для RLE | `rawBytes - 1`; не вклався — плитка йде сирою (`tile.cpp:55`) |
| Серії | ідуть **наскрізь через увесь масив плитки**, а не по рядках (`rle16.cpp:29`) |
| Довжина серії | обрізається на **255** і продовжується наступною парою |
| Однотонна плитка 32×32 | 1024 пікселі = **5 серій** = 15 Б даних + 9 Б заголовка = **24 Б** |
| Сира плитка 32×32 | 2048 Б даних + 9 = **2057 Б** |

**⚠️ Стеля проти фактичного.**

- Виграш стиснення на інтерфейсі EdgeTX — **5–20×** (`docs/02-architecture.md`).
- **Середня плитка після RLE — 286 Б** (заміряно на TX16S, `tools/remote_ui_proto.py:266`).
- **Найгірша заміряна плитка — 392 Б**, у розрахунках округлено до 400 Б
  (задача 0018).
- Повний кадр: 91 плитка × 286 Б ≈ **25.4 КБ** проти 261 120 Б сирого, тобто
  ~10× (задача 0017).
- ⛔ **Апаратного стиснення немає ніде:** у F429 JPEG з'явився лише з F76x;
  апаратний CRC є, але поліном не наш; DMA2D є і вже задіяний EdgeTX.

⚠️ **Дрібніша плитка (16×16) не дала б виграшу на прокрутці:** там міняються
всі пікселі, тож дрібніша сітка не економить нічого, а додає вчетверо більше
заголовків (510 плиток замість 135). Виграш дрібної плитки — на **локальних**
змінах. Аргумент «дрібніша плитка вкорочує серії для RLE» **хибний** — серії
йдуть наскрізь. Дослід не проводився: **не міряно**.

## 5. Кадрування і CRC

**Що це.** Найнижчий шар протоколу — перетворення потоку байтів на пакети й
назад. `protocol.h`/`protocol.cpp`; дзеркала — `firmware/esp32/main/framing.{c,h}`,
`webui/proto.js`, `tools/remote_ui_proto.py`.

```
+------+------+------+--------+-----------+--------+
| 0xE7 | 0x7E | TYPE | LEN:2  | PAYLOAD   | CRC:2  |
+------+------+------+--------+-----------+--------+
                       LE       LEN байт     LE
```

**Характеристики й обмеження.**

| | |
|---|---|
| `MAX_PAYLOAD_SIZE` | **4096** |
| `FRAME_OVERHEAD` | **7 Б** (маркер 2 + тип 1 + довжина 2 + CRC 2) |
| `MAX_FRAME_SIZE` | **4103 Б** |
| CRC | CRC-16/CCITT-FALSE, поліном 0x1021, початок 0xFFFF, побітово (без таблиці) |
| Що входить у CRC | `TYPE + LEN(2 байти в дротовому порядку) + PAYLOAD`; маркер і сам CRC — ні |
| Контрольний вектор | порожній `PING` = `E7 7E 86 00 00 66 45` |
| Тайм-аутів на цьому шарі | **немає** — шар не знає, скільки минуло між байтами |
| Об'єкт `Decoder` | **4120 Б** (4096 із них — буфер найбільшого `PAYLOAD`) |

**⚠️ Точка ресинхронізації — місце свідомої втрати.** Після відкинутого кадру
пошук маркера починається з байта, **наступного за цим кадром**; уже
прочитаний `PAYLOAD` повторно не переглядається. Маркер у даних не
екранується.

Наслідок, прийнятий свідомо: **одна побита `LEN` може «з'їсти» до 4096
наступних байтів разом із валідними кадрами**, що там лежали. На 921600 бод це
до ~44 мс сліпоти, на 2 625 000 — до ~15.6 мс, після чого потік відновлюється
сам. Саме через цю діру існує `INPUT_STATE` (рівень, а не перехід) — див.
розділ 14.

**Скид за тишею — обов'язок транспортного шару.** Три примірники числа мусять
збігатися, бо воно описує **протокол**, а не трубу:

| Де | Константа | Значення |
|---|---|---|
| Пульт | `SILENCE_RESET_MS` | 100 мс |
| Міст | `BRIDGE_SILENCE_RESET_MS` | 100 мс |
| Інструменти на ПК | `SILENCE_RESET_S` | 0.100 с |

**⚠️ Стеля проти фактичного.**

- Помилок CRC на дроті за 28-хвилинний сеанс на 2 625 000: **0** із 79 700
  пакетів, 18 397 185 Б (задача 0017). За 11-хвилинний сеанс задачі 0021 —
  теж **0**.
- Похибка дільника базової 921600 — **+1.273 %** на пульті (подвійне обрізання
  в макросі LL) проти бюджету приймача 3.33 %. Це **найбільша** розбіжність
  усього переліку швидкостей, і вона працює з нулем помилок.

## 6. USART3 + DMA — фізичний канал AUX1

**Що це.** Зовнішній 4-піновий роз'єм знизу пульта: `GND / 5V / TX / RX`.

**Характеристики й обмеження.**

| | AUX1 | AUX2 |
|---|---|---|
| Контролер | **USART3** | USART6 |
| TX / RX | PB10 / PB11 | PG14 / PG9 |
| **DMA на передачу** | ✅ DMA1, Stream3, Ch4 | ❌ **немає** |
| DMA на прийом | DMA1, Stream1, Ch4 | DMA2, Stream1, Ch5 |
| Керування живленням | PA15 | PB0 |

- **Рівні сигналів — 3.3 В** (прямо з ніжок STM32F429), попри назву «5v UART
  port». ESP32 підключається напряму, перетворювач рівнів не потрібен.
- **Керування потоком недоступне:** RTS/CTS на роз'єм не виведено. Зворотний
  тиск тільки програмний.
- ⚠️ **Режим `REMOTE_UI` доступний тільки на AUX1.** VCP виключено: у драйвері
  USB CDC `sendBuffer` і `getByte` нульові, а `usbSerialPutc()` при
  переповненні мовчки затирає кільце. AUX2 виключено: там немає `txDMA`, і
  драйвер пішов би запасним шляхом «по байту через чергу на 512 байтів», яка
  при переповненні **мовчки викидає** решту. Перевірка **продубльована** в
  гачку 4 і в `portUsable()` — свідомо, бо `radio.yml` тут правлять наосліп.
- ⚠️ Буфер передачі мусить лежати в секції `.ram` (макрос `__DMA`), інакше
  `_IS_DMA_BUFFER()` не пройде і драйвер мовчки перейде на побайтовий шлях із
  тихою втратою байтів.

**⚠️ Стеля проти фактичного.**

Ємність каналу рахується як `бод / 10` — при 8N1 на дроті **десять** біт на
байт, а не вісім.

| Швидкість | Ємність | Заміряне навантаження | Частка |
|---|---:|---|---:|
| 921 600 (домашня) | **92 160 Б/с ≈ 90 КБ/с** | 81.1–81.5 КіБ/с (рух, повна перемальовка) | **88.5–90.5 %** |
| 921 600 | | 69 КБ/с (гортання, задача 0019) | 75 % |
| 2 625 000 (стеля) | **262 500 Б/с ≈ 256 КБ/с** | 154–172.5 КБ/с (прокрутка, задача 0017) | **60–67 %** |
| 2 625 000 | | 145 КБ/с (гортання енкодером 8 клацань/с) | 55 % |
| 2 625 000 | | 41 КБ/с (протяг пальцем), 54 КБ/с (енкодер) — задача 0020 | **16–21 %** |
| 2 625 000 | | 0.5 КБ/с (нерухомий екран) | 0.2 % |

⚠️ **Стеля швидкості каналу — 2 625 000 бод, і це умова, а не просто межа.**
AUX1 — це USART3 на шині PCLK1, яку EdgeTX тактує **42 МГц**, не 45
(`f4/system_clock.c:85`, `LL_RCC_APB1_DIV_4` при SYSCLK 168 МГц;
`targets/horus/hal.h:25` — те саме число незалежно). 2 625 000 = 42 МГц / 16.
За цією межею драйвер перейшов би на дискретизування ×8 і писав би `CR1.OVER8`
при увімкненому USART, чого RM0090 не дозволяє. Тримається двома
`static_assert`, один звіряє стелю з `PERI1_FREQUENCY` цілі.

⛔ **Плавності 25 кадр/с на цьому транспорті не буде, і це арифметика.** Повний
кадр ≈ 25.4 КБ, ємність 256 КБ/с → стеля **≈10 повних кадр/с**. Для 25 кадр/с
потрібно у 2.5 раза більше за **апаратну** межу AUX1.

## 8. Розбирач моста і накопичувач пачок

**Що це.** Міст **не тлумачить вмісту** пакетів — він не знає ні розміру
екрана, ні RLE. Але межі пакетів знати мусить: відкидати можна тільки цілими
пакетами, інакше клієнт з'їв би обірваний кадр і за правилом ресинхронізації
втратив би ще до 4096 байтів. `framing.c`, `main.c:118`.

**Характеристики й обмеження.**

| | |
|---|---|
| Розмір пачки `BRIDGE_WS_CHUNK_BYTES` | **8192 Б** |
| Що в пачці | щонайбільше **два** пакети протоколу (стеля одного — 4103 Б) |
| Коли пачка віддається | (а) не влазить наступний пакет; (б) прийшов `FRAME_END`; (в) наприкінці кожного читання UART |
| Пакет із хибним CRC | далі не йде взагалі |
| Скид розбирача за тишею | 100 мс (`BRIDGE_SILENCE_RESET_MS`) |

⚠️ **`FRAME_END` віддається негайно**, окремим викликом `chunk_flush()` — саме
він дозволяє клієнту показати кадр, і затримка тут була б затримкою рівно там,
де її видно оком.

**Лічильники, які тут ведуться:** `packets_ok`, `crc_errors`, `oversized`,
`tiles_in`, `frames_in`, `silence_resets`, `chunks_built`,
`chunk_bytes_built`, `chunk_len_max`.

**⚠️ Стеля проти фактичного.**

- Стеля пачки 8192 Б; **найбільша зібрана пачка** за сеанс задачі 0021 —
  **3869 Б**.
- ⚠️ Розбирач моста скидається за тишею обов'язково: без цього пульт,
  вимкнений посеред плитки, лишив би розбирач назавжди застряглим у стані
  «дочитую вантаж», і він з'їв би початок потоку після ввімкнення — зокрема
  `HELLO` для нового телефона.

## 9. Черга до Wi-Fi і `ws_tx_task`

**Що це.** Скінченна кільцева черга розрізає шлях надвоє: приймання з UART не
має права блокуватись, а віддача у Wi-Fi має право чекати. `main.c:59,225`.

```
UART ──► rx_task ──► черга ──► ws_tx_task ──► Wi-Fi
         (не чекає)  (скінченна) (має право чекати)
```

**Характеристики й обмеження.**

| | |
|---|---|
| Розмір черги `BRIDGE_WS_RING_BYTES` | **24 576 Б (24 КіБ)** на ESP32; 12 288 Б на C3 |
| Тип | `RINGBUF_TYPE_NOSPLIT` |
| `ws_tx_task` | пріоритет **6**, стек 4096, очікування елемента 200 мс |
| Пріоритет задачі httpd (чуже число) | **5** (`tskIDLE_PRIORITY + 5`) |
| Пріоритет сторожа | **4**, період 100 мс, стек 3072 |

⚠️ **Це не накопичення кадру.** Повний кадр екрана — 255 КБ і не влазить у
жодну з плат; у черзі лежить щонайбільше 24 КБ.

⚠️ **Черга формально стоїть вище за задачу httpd, яка чує ввід.** Це був
перший підозрюваний у затримках вводу — і його **спростовано заміром**, а не
міркуванням: биття в задачу сервера показало 132 мс під тим самим
навантаженням, за якого паузи вводу сягали 4196 мс. Пріоритети лишаються як
були.

**⚠️ Стеля проти фактичного.**

- Переповнення черги — **єдине місце в мості, де щось відкидається**, і воно
  рахується: `chunks_dropped`, `tiles_dropped`, `packets_dropped`.
- `ring_free_min` — найменше вільне місце: **8700 Б** із 24 576 за сеанс
  задачі 0021 проти найбільшої пачки 3869 Б, тобто черга **не впиралась**.
- ⚠️ За 28-хвилинний сеанс задачі 0017 (2 625 000, один клієнт) до телефона
  **не доїхало 1059 плиток і 133 пачки**, тоді як дріт дав нулі на всіх
  лічильниках. Пізніші сеанси (0019, 0021) дали нулі й тут.

**⚠️ Три різні події, які легко сплутати.**

| Подія | Що робить міст | Чому |
|---|---|---|
| Невдале відправлення | **викидає пачку** (`send_dropped`), сокет живий | серед причин — банальне переповнення вікна TCP |
| Обрізаний кадр WebSocket | **рве сокет** | кадрування WebSocket самосинхронізації не має; клієнт читав би вантаж як заголовок |
| Мовчання клієнта 750 мс | **відпускає ввід, сокет лишає** | «ввід застарів» і «телефона немає» — різні висновки |

недописаним:** `httpd_ws_send_frame_async` перевіряє лише `< 0`, а lwIP із
виставленим `SO_SNDTIMEO` повертає **часткове відправлення як успіх**. Тому

⚠️ **Ціна сторінки в пам'яті моста дорівнює її розміру на дроті.** Тому клієнт
стискається gzip на збірці — **122 КБ → 41 КБ**, розпаковує браузер, у мості
нуль рядків на розпакування. До цього мінімум вільної купи був **2 500 Б**.
Витоку немає: рівень повернення 106 408 Б однаковий у 1-шу і 11-ту хвилину
під навантаженням 19.8 МБ.

⛔ `CONFIG_LWIP_TCP_SND_BUF_DEFAULT` **не чіпаємо**: якщо пам'яті колись
забракне, перший важіль — обмежити кількість одночасних сокетів, бо небезпека
це **множення на кількість сокетів**, а не розмір буфера.

**⚠️ Стеля проти фактичного (Wi-Fi як труба).**

- ⛔ **Wi-Fi не додає затримки взагалі.** Повна перемальовка через міст —
  **1096 мс** проти дротових 1149; дрібна зміна — **88 мс** проти 95
  (задача 0012).
- Найбільший заміряний потік до телефона — **145 КБ/с** (задача 0019).
- Стеля «123 КБ/с», яку колись вважали межею, виявилась **станом, а не
  межею**: пізніші прогони дали 178–190 КБ/с без жодної втрати.
- Пропускна здатність самого радіоканалу на 8.5 дБм — **не міряно**.

## 11. Браузер: приймання й розбір

**Що це.** Сторінка клієнта живе у флеші моста і віддається браузеру стисненою
gzip. Розбір протоколу — `webui/proto.js`, застосунок — `webui/app.js`.

### Хто говорить першим

⚠️ **Над послідовним портом першим завжди говорить клієнт.** У порту немає
події «клієнт підключився»: він відкритий рівно тоді, коли пульт увімкнено, і
на іншому кінці може не бути навіть дроту. Сипати туди кадрами пульт не має
права.

```
клієнт → PING
пульт  → HELLO        (розмір екрана, клавіші, прапорці, перелік швидкостей)
клієнт → REFRESH      (тепер він знає, куди класти пікселі)
пульт  → плитки … FRAME_END
```

Просити `REFRESH` до `HELLO` безглуздо: клієнт не знає розміру екрана й
викине всі плитки.

**Що несе `HELLO`** (`hello.h`, `proto.js:349`):

| Поле | Розмір | Звідки в EdgeTX |
|---|---:|---|
| версія протоколу (=1) | 1 Б | — |
| ширина, висота | 2 + 2 Б | `LCD_W`, `LCD_H` |
| формат пікселя (1 = RGB565) | 1 Б | — |
| прапорці: біт0 сенсор, біт1 енкодер, біт2 файлові операції, **біт3 `INPUT_STATE`** | 1 Б | — |
| кількість тримерів | 1 Б | `keysGetMaxTrims()` |
| маска підтримуваних клавіш | 4 Б | `keysGetSupported()` |
| перелік клавіш: код + підпис | 1 + 16 Б на клавішу | `keysGetLabel()` |
| назва цілі | 32 Б | `FLAVOUR` |
| версія EdgeTX | 16 Б | `VERSION` |
| поточна швидкість, домашня, N і сам перелік | 4 + 4 + 1 + 4·N Б | `baudrate.h` |

**Специфіки конкретного пульта в коді — нуль рядків.** На TX16S у переліку
7 клавіш: `RTN`, `Enter`, `PAGE<`, `PAGE>`, `MDL`, `TELE`, `SYS`. Новий пульт
дає робочі панелі без оновлення застосунку.

⚠️ `REFRESH` **завжди** завершується `FRAME_END`, навіть якщо на екрані
нічого не змінилося. Інакше найтиповіший випадок — підключення до пульта, що
спокійно стоїть на головному екрані, — виглядав би як мертвий зв'язок при
живому.

**Характеристики й обмеження.**

| | |
|---|---|
| Сокет | один, `ws://<host>/ws`, `binaryType = 'arraybuffer'` (`app.js:593`) |
| Потік виконання | **головний потік браузера**; ані Web Worker, ані `OffscreenCanvas` не використовуються |
| Накопичувач недочитаного | `Decoder.buf` (`proto.js:280`); при порожньому хвості розбір іде **прямо по вхідному масиві**, без копіювання |
| Стеля накопичувача | явної **немає**; неявна — незакритий кадр не довший за 7 + 4096 Б |
| CRC | той самий CRC-16/CCITT-FALSE, але **за таблицею на 256 записів** (`proto.js:185`), а не побітово, як у прошивці |
| Перепідключення | `RECONNECT_MS = 1000` (`app.js:17`) |
| Вітання | `PING` раз на `GREET_RETRY_MS = 500` мс, доки не прийде `HELLO`; на 6-й спробі (≈3 с) завіса каже «пульт не відповідає» |
| Сторож зв'язку | `PING` раз на 2000 мс; мовчання понад 5000 мс → примусовий `ws.close()` і перепідключення |

**Ресинхронізація в клієнті — та сама, що в прошивці й у мості:**

| Випадок | Що робить клієнт | Лічильник |
|---|---|---|
| маркера в буфері немає | лишає **останній 1 байт** (може бути половина маркера) | — |
| кадр іще не дочитано | лишає хвіст і чекає | — |
| CRC не зійшовся | пропускає **весь** кадр, шукає маркер за ним | `crcErrors` |
| `LEN > 4096` | пропускає 5 байтів (маркер+тип+довжина) | `oversized` |
| невідомий тип | мовчки ігнорує (правило сумісності) | — |

**Лічильники прикладного рівня** (`app.js:48`): `tiles`, `badTiles`,
`outOfBounds`, `beforeHello`, `frames`, `autoRefresh`, `encClicks`,
`keyPresses` і шість «кадрових» — `framesWhole`, `framesTimeout`,
`framesTooMany`, `framesNoWait`, `framesDrag`, `framesLegacy`. ⚠️ Сума цих
шести **дорівнює** `frames` рівно; невідома причина показу кидає виняток.

**Розтиснення й малювання.**

- `decodeTile()` (`proto.js:502`) розбирає заголовок 9 Б і розтискає RLE16;
  бита плитка повертає `null`, а не кидає виняток.
- `blitTile()` (`proto.js:551`) переводить RGB565 → RGBA **повторенням старших
  бітів** (`(r << 3) | (r >> 2)`), а не множенням — щоб 0x1F давало рівно 255.
- Плитка, що не влазить у буфер, відкидається з `outOfBounds++`.

**⚠️ Стеля проти фактичного.**

- Пікселі **не масштабуються**: `putImageData` пише 1:1 у canvas 480×272, а
  розтягує його CSS (`fitCanvas()`, коефіцієнт `min(ширина/W, висота/H)`,
  не менший за 0.1), зі згладжуванням, вимкненим через `image-rendering:
  pixelated`.
- Час розбору й малювання клієнт міряє сам (`prof.msFeed`, `prof.msTile`,
  `prof.msDraw`) і показує як «зайнятість» із порогами 50 % (жовтий) і
  80 % (червоний). ⚠️ Конкретне значення зайнятості на телефоні —
  **не міряно** (у задачах немає).
- Тестовий клієнт на tkinter витрачав **3.5 мс на кадр** 480×272, тобто вікно
  не було вузьким місцем (задача 0006). Для браузера аналогічного числа
  **не міряно**.

## 12. Буфер кадру й показ за політикою очікування

**Що це.** Плитки лягають у позаекранний буфер безперервно; чекає **лише
показ**. Буфер — `ImageData` на весь екран (`app.js:46`), створений через
`ctx.createImageData()`, з альфою, примусово виставленою в 255.

Показ відбувається **тільки** на `FRAME_END`, синхронно в тому самому
обробнику повідомлення WebSocket — без `setTimeout` і без
`requestAnimationFrame`.

**`FRAME_END` несе `dirtyTiles`** — скільки плиток лишилось незасланими на мить
закриття кадру, 2 байти LE.

| Вантаж `FRAME_END` | Що робить клієнт |
|---|---|
| менше 2 байтів | ознаки немає (стара прошивка) — **показати негайно** (`WHY_LEGACY`) |
| 2 і більше | прочитати перші 2 байти, решту проігнорувати |

**Що гарантує `dirtyTiles = 0`.** Якщо канал нічого не загубив, буфер клієнта
**дорівнює екрану пульта на мить закриття кадру** — це один справжній момент,
а не зшивка. Плитка завжди несе найсвіжіший відомий вміст своєї клітинки, а
клітинка, якої не міняли, лишається правильною скільки завгодно довго. Зшивку
створює не старість плитки, а **недоставлена новіша версія** — саме її й
рахує `dirtyTiles`.

**Політика очікування** — окремий модуль без DOM `webui/wait.js`, із близнюком
на Python (`tools/remote_ui_proto.py`) і перехресною перевіркою
`tools/wait_crosscheck.py`, де очікуваних значень немає взагалі: еталон одного
клієнта — другий клієнт.

Порядок правил у `decide(dirty, now)` жорсткий (`wait.js:230`):

| # | Умова | Результат |
|---|---|---|
| 1 | `dirty === null` (стара прошивка) | показ, `WHY_LEGACY` |
| 2 | `dirty === 0` | показ, `WHY_WHOLE` |
| 3 | режим `WAIT_OFF` | показ, `WHY_OFF` |
| 4 | зараз протяг пальцем | показ, `WHY_DRAG` |
| 5 | режим `WAIT_LIMIT` і `dirty > поріг` | показ, `WHY_TOO_MANY` |
| 6 | інакше — рахуємо строк; вичерпано | показ, `WHY_TIMEOUT` |
| | інакше | **чекаємо** |

**Числа політики.**

| Константа | Значення | Де | Звідки число |
|---|---:|---|---|
| `FRAME_WAIT_BASE_MS` | **50** | `proto.js:95` | те, що від `N` не залежить: пачка в польоті 15.6 мс, прохід транспорту 2 мс, пачка моста 7 мс, Wi-Fi 5 мс, цикл подій браузера 16 мс |
| `FRAME_WAIT_PER_TILE_MS` | **3** | `proto.js:96` | одна плитка наскрізно в найгіршому заміряному стані каналу: 400 Б при 123 КБ/с |
| `FRAME_WAIT_MAX_MS` | **250** | `proto.js:97` | стеля, ≈2.5 повних кадри дроту |
| `FRAME_WAIT_TILE_BYTES` | **286** | `proto.js:145` | заміряна середня плитка 32×32 після RLE |
| `RADIO_FRAME_MS` | **50** | `proto.js:156` | округлення вниз від заміряних 58 мс (17.1 `FRAME_END`/с у 0018) |
| `TOUCH_NOWAIT_MS` | **1000** | `wait.js:81` | хвіст інерції LVGL: `scroll_throw` = 10, опитування раз на 30 мс → найшвидший правдоподібний поштовх їде ≈900 мс |
| `TOUCH_DRAG_LIMIT_PX` | **10** | `wait.js:99` | дорівнює `LV_INDEV_DEF_SCROLL_LIMIT` — тим самим, яким пульт відрізняє гортання від натискання |

```
T_wait(N) = min(50 мс + 3 мс × N,  250 мс)
але не більше, ніж лишилось від початку ПОТОЧНОЇ НИЗКИ очікування
```

⚠️ Стеля рахується **від початку низки**, а не від кожного `FRAME_END` (тоді
безперервне гортання заморозило б екран назавжди) і не від останнього
показаного кадру (тоді після паузи на нерухомому екрані запас був би вже
вичерпаний, і головний випадок лишився б не покритим).

⚠️ **`T_wait` — бюджет доїзду, а не прогноз спорожніння карти.** Коли бруднення
стабільно перевищує ємність каналу, карта не порожніє за побудовою і строк
стає штатною гілкою. Піднімати стелю в цьому режимі безглуздо.

**Правило протягу.** Клієнт знає, чим щойно керували, бо сам це надіслав:
після `ENC`, клавіші, тику або тиші — **чекаємо** цілого кадру; під час
протягу пальцем — **показуємо негайно**, бо людина стежить за рухом, а не за
чіткістю кадру. Вікно «не чекати» — 1000 мс після останнього пакета дотику.
⚠️ Періодичний `INPUT_STATE` навмисно **не** відсуває це вікно: інакше забутий
на екрані палець тримав би його нескінченно.

**Поріг «не чекати взагалі».**

```
поріг = floor( (бод / 10) × (50 мс / 1000) / 286 Б )
        2 625 000 → 45 плиток;  921 600 → 16 плиток;  швидкість невідома → 45
```

⚠️ Тут 1.1 мс на плитку (дріт), а в строку очікування — 3 мс (наскрізно до
телефона). Це **не** суперечність: поріг **порівнює** доїзд залишку з доїздом
наступного кадру, а конвеєр затримує обидва однаково й у порівнянні
скорочується.

⛔ **Поріг як важіль закрито числами.** `dirtyTiles` ніколи не наближається до
розміру сітки (стеля ~96 зі 135), а всі режими керування лежать у діапазоні
80–96 і порогом **не розділяються**. Показ за строком не стався жодного разу
ні за якого порога. Чинний типовий режим — **`WAIT_ALWAYS`, «чекати завжди»**.

**⚠️ Стеля проти фактичного.**

| Замір (задача 0019, той самий жест, 20 с, той самий екран) | 2 625 000 | 921 600 |
|---|---:|---:|
| Потік до телефона | 142 КБ/с | 69 КБ/с |
| Кадрів показано | 137 | 121 |
| З них **цілих** (`dirtyTiles = 0`) | **137 (100 %)** | 75 (62 %) |
| З них **показано за строком** (зшитих) | **0** | **46 (38 %)** |

⚠️ **«100 % цілих кадрів» — властивість швидкості 2 625 000, а не механізму.**
Після кожного перезапуску стенда пульт удома на 921 600, і поки клієнт не
замовив високу швидкість, шви є — і це **не регресія**. Підтверджено сліпим
розпізнаванням: людині показали два прогони, не кажучи який із чим, і вона
назвала фризи рівно там, де їх бачили лічильники.

Ціна очікування, названа числом: **8.8 → 6.6 показів за секунду** при
гортанні, за те, що жоден показаний кадр не зшитий.

**Автоматичний `REFRESH` за втратами.** Клієнт раз на секунду читає
`/api/stats` моста і, побачивши приріст `ws.packets_dropped`, просить `REFRESH`:

| Умова | Значення |
|---|---|
| Період опитування `/api/stats` | 1000 мс |
| «Картинка вгамувалась» | 500 мс від останнього показаного кадру |
| Придушення повторного `REFRESH` | не частіше ніж раз на **2000 мс** |

⚠️ Придушення обов'язкове: на вузькому каналі `REFRESH` годує сам себе.
Причина, з якої це взагалі потрібно: `FRAME_END` проходить, плитки того ж
кадру відкинуто мостом, клієнт показує кадр цілісним — а пульт ту плитку
більше не надішле, бо шле лише зміни. Прямокутник зі старими пікселями лишався
б назавжди.

# Частина II. Пайплайн керування

Зворотний напрямок майже порожній за трафіком (десятки–сотні байтів за
секунду) і критичний за затримкою. Головне правило: **емульований ввід
додається до фізичного (`|=`), ніколи не заміщує.** Фізичні клавіші пульта
працюють завжди, хоч би що робив клієнт і чи він узагалі живий.

## 13. Подія в браузері й намір

**Що це.** Органи керування в клієнті виражають **намір**, а чим його
виконати — вирішує перелік клавіш із `HELLO`. Рядків про TX16S у коді нуль.
`webui/panels.js`.

⚠️ **Бокові панелі — задача 0022, етап 3, у роботі.** `webui/panels.js` і
`webui/panels_test.js` на момент написання документа ще не в комітах.

**Наміри:** `up`, `down`, `left`, `right`, `select`, `back`, `page-prev`,
`page-next`.

**Розкладання за `HELLO`** (`resolveIntents()`, `panels.js:119`):

| Намір | Синоніми в підписах клавіш | Гілка «стрілок немає» (TX16S) |
|---|---|---|
| `up` / `down` | `UP` / `DOWN` | **клацання енкодера** −1 / +1 |
| `left` / `right` | `LEFT` / `RIGHT` | **не показуються зовсім** |
| `select` | `ENTER`, `OK` | `Enter` |
| `back` | `RTN`, `EXIT` | `RTN` |
| `page-prev` / `page-next` | `PAGE<`, `PGUP` / `PAGE>`, `PGDN` | свої кнопки на панелі |

⛔ **Вліво-вправо ніколи не стають сторінками** — ні на джойстику, ні на
клавіатурі. Сторінки перемикаються лише своїми кнопками, на клавіатурі —
`PageUp`/`PageDown`.

**Розкладка панелей** (`SIDE_ORDER`, `panels.js:82`) — бажане розташування для
цього пульта, а не зашита специфіка: клавіша, якої немає у вітанні, не
показується, невідома клавіша отримує місце в кінці лівої панелі.

| Бік | Зверху вниз |
|---|---|
| ліва | `SYS`, `RTN`, `PAGE>`, `PAGE<`, `TELE` |
| права | `MDL`, джойстик |

**Розгін енкодера в клієнті** (`panels.js:206`):

| Константа | Значення |
|---|---:|
| `ENC_FIRST_MS` | **260** мс |
| `ENC_FAST_MS` | **70** мс |
| `ENC_RAMP` | **0.82** |

```
encDelay(clicks) = max(70, round(260 × 0.82^clicks))
низка проміжків: 260, 213, 175, 143, 118, 96, 79, далі стеля 70 мс
```

⚠️ **Стеля — ≈14.3 клацання за секунду.** Прискорення кроку робить **не** цей
множник, а сам EdgeTX: він рахує крок із проміжку між клацаннями. Пачка з
нульовими проміжками дала б протилежний ефект — застиглий максимум
прискорення.

**Колесо миші** (тільки браузер на ПК, `app.js:1049`): `WHEEL_NOTCH_PX = 25`,
`WHEEL_TRACKPAD_PX = 40`; одна подія колеса = **рівно одне** клацання,
незалежно від величини `deltaY`.

**Клавіатура** (`KEYBOARD_INTENT`, `app.js:1101`): `ArrowUp/Down/Left/Right`,
`Enter`, `Escape`, `PageUp`, `PageDown`. `ev.repeat` **ігнорується** —
автоповтор дає EdgeTX або наш розгін.

**Множина тримачів.** Клієнт веде `Map` утримуваних цілей (`app.js:873`);
пульт дізнається про відпускання лише коли відпустив **останній** тримач
(панель, клавіатура, миша можуть тримати одне й те саме).

## 14. Пакети вводу і повний стан

**Що це.** Чотири пакети переходів і один пакет рівня.

| Пакет | Розмір вантажу | Вміст |
|---|---:|---|
| `0x81 KEY` | 2 Б | код клавіші (`EnumKeys`), 1 = натиснуто / 0 = відпущено |
| `0x82 ENC` | 1 Б | зсув, знаковий `int8`, зазвичай ±1 |
| `0x83 TOUCH` | 5 Б | подія (0=DOWN, 1=MOVE, 2=UP), x, y — `int16` LE, **знакові** |
| `0x85 TRIM` | 2 Б | індекс напрямку тримера, натиснуто/відпущено |
| `0x87 INPUT_STATE` | **13 Б** | маска клавіш (4), маска напрямків тримерів (4), прапорці дотику (1), x (2), y (2) |
| `0x86 PING` | 0 Б | перевірка живого пульта, у відповідь `HELLO` |
| `0x84 REFRESH` | 0 Б | усі плитки + обов'язковий `FRAME_END` |

⚠️ **Координати дотику знакові.** Пульт обрізає координати по екрану, і `-1`
при знаковому читанні стає нулем, а при беззнаковому — 65535 і обрізається до
**протилежного краю екрана**. Помилка клієнта на піксель уліво відправила б
палець у правий край.

**`INPUT_STATE` — рівень, а не перехід.** Клієнт шле його **раз на 250 мс
безумовно**, поки з'єднання живе, а не «поки щось утримується».

| | |
|---|---|
| Період | **250 мс** (`INPUT_STATE_PERIOD_MS`) |
| Ціна в каналі | 13 Б вантажу, **20 Б на дроті**, чотири рази на секунду = **80 Б/с** |
| Частка від ємності 2 625 000 | 0.03 % |

**Навіщо він потрібен.** Тайм-аут відпускання закриває тишу **всього** каналу,
але не закриває втрачений поодинокий пакет «відпущено» при живому зв'язку. Це
не гіпотеза: одна побита `LEN` з'їдає до 4096 байтів разом із валідними
кадрами, що там лежали (розділ 5). Рівень самолікує таку втрату за один період.

⚠️ **Лікувальний пакет надходить саме від клієнта, який вважає, що не утримує
нічого** — адже «відпущено» він уже надіслав, воно й загубилось. Тому
періодичність, прив'язана до «щось утримується», лікувала б рівно ті випадки,
яких не буває.

**Правило довжини `INPUT_STATE`:**

| Вантаж | Що робить пульт |
|---|---|
| менше 13 Б | ⚠️ **відкинути пакет цілком і тайм-аут не відсувати** |
| рівно 13 Б | застосувати |
| більше 13 Б | узяти перші 13, решту проігнорувати |

**Чотири правила застосування, на яких тримається все:**

1. **Клавіші й тримери — присвоєнням.** Маска заміщує «утримується зараз»;
   саме присвоєння і є зняттям залипання.
2. ⚠️ **Защіпнуте натискання пакет не чіпає ніколи.** Засувку гасить лише той,
   хто ввід читає. Інакше `INPUT_STATE`, що прийшов між `KEY` «натиснуто» і
   опитуванням клавіш, з'їв би коротке натискання цілком.
3. ⚠️ **Дотик застосовується тільки переходом, ніколи присвоєнням.** Рівень
   «пальця немає» при внутрішньому стані «унизу» **дописує** `UP` у чергу;
   присвоєння повз чергу стерло б непрочитаний `DOWN` і лишило б LVGL
   натиснутим назавжди.
4. **Енкодера в пакеті немає.** Він накопичувальний: втрата клацання коштує
   клацання, а не залипання. Заміщення накопичувача рівнем дало б фантомний
   оберт назад.

**Як клієнт дізнається, що прошивка це вміє — біт3 у прапорцях `HELLO`:**

| Біт3 | Що робить клієнт |
|---|---|
| 1 | шле `INPUT_STATE` раз на 250 мс, `PING` — раз на 2 с |
| 0 | `INPUT_STATE` не шле; щоб утримувати ввід, шле `PING` раз на 250 мс, поки щось утримується |

⚠️ **`TRIM` браузерний клієнт зараз не надсилає взагалі** — кодувальник і
дзеркало стану є, викликів немає. Тримери доступні лише через `INPUT_STATE`
(маска), тобто фактично не використовуються. Це стан задачі 0022, не рішення.

## 15. Шлях назад: браузер → міст → пульт

**Що це.** Найкоротша ланка конвеєра: міст **не тлумачить** ввід, а пересилає
як є.

```
браузер ──WebSocket──► httpd (пріоритет 5) ──► uart_link_write() ──► UART ──► пульт
                              │
                              └─► rui_scanner_feed() — лише щоб знати типи
```

**Характеристики й обмеження.**

| | |
|---|---|
| Стеля кадру від клієнта | **1024 Б**; більший кадр → міст рве з'єднання |
| Найбільший реальний пакет | `INPUT_STATE`, **20 Б** на дроті |
| Приймаються тільки | двійкові кадри WebSocket; текстовий ігнорується |
| Черга передачі в драйвері UART моста | немає (`tx_buffer_size = 0`) — чекати доводиться лише апаратну чергу 128 Б |
| Замок на запис | не потрібен: драйвер UART бере власний м'ютекс |

⚠️ **Живим клієнта роблять тільки пакети, що несуть ввід** — `KEY`, `ENC`,
`TOUCH`, `TRIM`, `INPUT_STATE`. `PING` і `REFRESH` — ні, і це те саме правило,
що діє в прошивці пульта.

**Прилад для затримки вводу** (`gap_*` у `/api/stats`): міст міряє паузу між
пакетами вводу **в момент, коли пакет розібрала задача httpd**. Розкладка:
`gap_le_300`, `gap_le_500`, `gap_le_750`, `gap_over`, `gap_max_ms`.

**⚠️ Стеля проти фактичного — заміри задачі 0013 (10 хв, 90 % завантаження
каналу на 921600, рівно один клієнт):**

| Що міряли | Результат |
|---|---:|
| Паузи вводу, які **бачить міст** | до **4196 мс**, 8 разів понад поріг 750 мс |
| Ті самі паузи, які **бачить клієнт** | максимум **301 мс**, понад поріг — нуль |
| Затримка задачі, що чує ввід (`beat_interval_max_ms`) | **132 мс** проти 129 у спокої |
| `ping` у тому самому вікні | 1142 відгуки, максимум **356 мс**, понад 750 — жодного |
| Втрачених пакетів | **нуль** — лічильники обох боків збіглися |

⚠️ **Висновок:** клієнт слав вчасно, ефір був вільний, задача моста не
голодувала — лишається сама труба. **Ввід і пікселі поділяють одне з'єднання
TCP**, і насичений потік пікселів затримує ввід на секунди; пакети приїжджають
пачкою. Пояснення прийнято як **гіпотезу**, не як висновок: вирішальний доказ
(`tcpdump` із видимими повторними передачами) не знімався.

⛔ Симптом **перестав відтворюватись** після переходу на 2 625 000: під
протягом канал завантажений на 16–21 %, і сторож мовчання не спрацював
жодного разу. Задача 0015, яка мала його ловити, закрита — предмет зник.
**Умова відкриття наново:** сторож мовчання спрацював при живому клієнті.

Якщо повторні передачі колись підтвердяться, розв'язок — **дейтаграмний канал
для вводу**, а не другий WebSocket: `INPUT_STATE` за побудовою є рівнем і
повторюється кожні 250 мс, тобто повторна передача йому не потрібна взагалі,
а саме вона й створює секундні паузи.

## 16. Розбирач у пульті й `InputState`

**Що це.** Той самий `Decoder`, що й для вихідного напрямку (розділ 5); пакети
вводу розбирає `applyInputPacket()` і застосовує до єдиного статичного
екземпляра `InputState`. `firmware/edgetx-patch/remote_ui/input.{h,cpp}`.

**Двоє учасників, без м'ютексів:**

```
потік транспорту  →  onKey / onTrim / onEncoder / onTouch / onInputState   пише
задачі EdgeTX     →  takeKeys / takeTrims / encoderOffset / popTouch       читає й споживає
```

Читач працює у **двох різних** задачах EdgeTX (клавіші — 10-мілісекундна
службова задача, сенсор і енкодер — LVGL у `menusTask`), але їхні частини
стану не перетинаються.

**Характеристики й обмеження.**

| | Значення | Чому |
|---|---:|---|
| `INPUT_STATE_PERIOD_MS` | 250 | вимога протоколу до клієнта |
| `INPUT_RELEASE_TIMEOUT_MS` | **1000** | чотири пропущені періоди; `static_assert` тримає зв'язок |
| `ENCODER_DT_IDLE_MS` | **500** | стільки приписується клацанню, перед яким була пауза — 500 мс дають нульове прискорення |
| `TOUCH_HISTORY` | **8** переходів | рухи (`MOVE`) сюди не потрапляють, тому переповнити потоком рухів неможливо |
| `INPUT_MAX_BITS` | **32** | клавіш у `EnumKeys` менше за 32; усе поза маскою відкидається на вході |

**⚠️ Чому клавіші зі «засувкою».** `keysPollingCycle()` читає клавіші раз на
10 мс. Клієнт може встигнути прислати «натиснуто» і «відпущено» **між** двома
читаннями — і натискання пропало б безслідно. Тому кожне натискання ще й
защіпається: читач обов'язково побачить його рівно один раз.

**⚠️ Чому в енкодера накопичувач, а не приріст.** Гачок додає наше значення до
положення фізичного енкодера, а EdgeTX рахує різницю з попереднім читанням.
Віддавши раз «+3» і потім нуль, ми отримали б наступним читанням «−3» — тобто
фантомний оберт назад. Накопичувач не обнуляється навіть при розриві.

⚠️ **Мінімальна тривалість дотику, яку пульт помічає, — ~100 мс** (заміряно в
задачі 0019): `LV_INDEV_DEF_READ_PERIOD` = 30 мс, і LVGL просто не потрапляє
опитуванням у коротше вікно. Робочий дотик у автоматичному приводі клієнта —
150 мс.

## 17. Підмішування у драйвери EdgeTX

**Що це.** Ми не «натискаємо кнопки» в GUI, а підмішуємо віртуальний стан у ті
самі місця, звідки читається фізичне залізо. Тоді безкоштовно отримуємо всю
логіку EdgeTX: коротке й довге натискання, автоповтор, прискорення енкодера,
блокування клавіш, звуковий відгук.

```
keysPollingCycle()  →  keys_input  |= remoteUiGetKeys()          раз на 10 мс
                       trims_input |= remoteUiGetTrims()
rotaryDriverRead()  →  newPos      += remoteUiGetEncoderOffset()  опитування LVGL
                       remoteUiAddEncoderDt(&rotencDt)
touchDriverRead()   →  remoteUiPopTouch(&x, &y, &pressed)         раз на 30 мс
```

**Характеристики й обмеження.**

| Гачок | Файл EdgeTX | Рядків | Період виклику |
|---|---|---:|---|
| 6. клавіші й тримери | `radio/src/keys.cpp`, `keysPollingCycle()` | 9 | **10 мс** (`per10ms()`) |
| 7. енкодер і сенсор | `radio/src/gui/colorlcd/LvglWrapper.cpp` | 24 | опитування LVGL, **30 мс** (`LV_INDEV_DEF_READ_PERIOD`) |

⚠️ **Саме `|=`, ніколи `=`.** Це межа проєкту, а не оптимізація.

⚠️ **`remoteUiAddEncoderDt(&rotencDt)` бере вказівник, а не повертає значення.**
З вказівником функція може **не робити запису взагалі**, поки віддалених
клацань немає — і тоді без клієнта фізична ручка поводиться точно як до
Remote UI.

⚠️ **Залишкова гонка, прийнята свідомо.** `*rotencDt += pending` не атомарне:
`rotencDt` пише ще й переривання енкодера. Вікно — три інструкції, і
відкривається лише коли віддалене клацання збігається з фізичним перериванням.
Найгірший наслідок — **одне фізичне клацання із завищеним прискоренням**;
положення й напрямок не зачіпаються. Прибрати можна тільки критичною секцією,
тобто виходом за один дозволений рядок у чужому файлі.

⚠️ **Гачок сенсора стоїть до перевірки `isBacklightEnabled()`** — інакше
застосунок не «розбудив» би пульт із вимкненою підсвіткою.

**Ціна всього патчу в чужому коді — 88 рядків у 9 файлах, усе вставки**
(`docs/05-hooks.md`).

**Ціна в пам'яті пульта** (за картою пам'яті збірки `X10`/`RADIO_TX16S`, не за
розрахунком):

| Пам'ять | Без `REMOTE_UI` | З `REMOTE_UI` | Різниця | Вільно після |
|---|---:|---:|---:|---:|
| Флеш | 1558.09 КБ | 1562.20 КБ | **+4.11 КБ** | 485.80 КБ із 2048 |
| Внутрішня ОЗП (`.bss` + `.ram`) | 67 088 Б | 82 064 Б | **+14 976 Б** | 114 544 Б із 196 608 |
| CCM (`.data` + стеки) | 50 936 Б | 52 984 Б | **+2 048 Б** | **12 552 Б** із 65 536 |
| SDRAM | 3 404 032 Б | 3 665 152 Б | **+261 120 Б** | ~4.5 МБ із 8 МБ |

⚠️ **Найтісніше — CCM: 80.85 % зайнято, 12.25 КБ вільно.** Наш стек задачі
транспорту з'їв 2 КБ із них.

## 18. Тайм-аути й відпускання вводу

**Що це.** Залипла емульована клавіша означає, що пульт натискає щось сам по
собі, а людина цього не бачить — екрана немає. Тому рубежів чотири, і кожен
працює незалежно від решти.

| # | Рубіж | Поріг | Хто виконує | Що робить |
|---|---|---:|---|---|
| 1 | Розрив сокета / витіснення / подія Wi-Fi | миттєво | міст | **негайно шле обнулений `INPUT_STATE`** |
| 2 | Сторож мовчання клієнта | **750 мс** | міст | шле обнулений `INPUT_STATE`; **сокет не рве** |
| 3 | Тайм-аут відпускання | **1000 мс** | **читач** у прошивці (задачі EdgeTX) | відпускає весь емульований ввід |
| 4 | «Клієнта більше немає» | **3000 мс** | задача транспорту в пульті | завершує сеанс, перестає передавати |

⚠️ **Тайм-аут відпускання перевіряє той бік, який ввід читає**, а не той, що
натискав. Тобто навіть якщо потік транспорту помер, завис у `send()` або його
зняли — клавіші все одно відпустяться.

⚠️ **Відсувають тайм-аут лише пакети, що несуть ввід.** `PING`, `REFRESH` і
невідомі типи — ні. Причина конкретна: між телефоном і пультом стоїть міст
ESP32, і він **власний посередник** — цілком може слати `PING` далі після
того, як телефон від'єднався. При правилі «будь-який пакет» клавіша,
утримувана в мить розриву Wi-Fi, лишилася б натиснутою назавжди.

**Порядок порогів навмисний:** 750 (міст) < 1000 (прошивка). Міст має помітити
втрату **раніше** за пульт і відпустити ввід сам, а не покластися на останню
перешкоду.

**⚠️ Стеля проти фактичного.**

- **Справжній розрив Wi-Fi на живому ESP32 — 184 мс** проти 1000 мс тайм-ауту
  прошивки (задача 0012). Міст помітив зникнення телефона **сам**, не
  покладаючись на останній рубіж.
- ⚠️ Телефон із заблокованим екраном **втрачає сокет приблизно за хвилину і не
  повертається**: у задачі 0013 ввід ішов рівно 45 с, потім сокет помер, і за
  наступні 4.5 хвилини перепідключення не було жодного. Безпека втрималась —
  ввід відпущено, — але **передумова рішення «сторож сокет не рве» на залізі
  не виконується**. Наслідок переїхав у клієнт: він **сам** перепідключається
  після пробудження і просить `REFRESH`.
- ⚠️ **Клієнт, що перестав читати, втрачає сокет мовчки:** пауза ~3 с у
  читанні дає розрив, при цьому `ws.errors` і `send_dropped` лишаються нулями —
  з'єднання скидає, найімовірніше, сам lwIP через RST. Чи вважати це вадою —
  **питання відкрите**.
- Утримання клавіші 10 секунд без розтискання — **не міряно** (критерій 4.2
  задачі 0022, ще не виконаної).

## Перемикання швидкості каналу на ходу

**Що це.** Швидкість каналу міняється командою протоколу за секунди, без
перепрошивання пульта. Орган керування — на сторінці моста. ADR-0005,
`remote_ui/baudrate.{h,cpp}`, `esp32/main/baud_follow.c`.

**Дозволені швидкості** (перелік закритий і живе в **прошивці**):

| Бод | BRR пульта | Похибка пульта | Похибка моста |
|---:|---:|---:|---:|
| **921 600** (домашня) | 45 | **+1.273 %** | +1.208 % |
| 1 000 000 | 42 | 0.000 % | 0.000 % |
| 1 500 000 | 28 | 0.000 % | −0.039 % |
| 2 000 000 | 21 | 0.000 % | 0.000 % |
| **2 625 000** (стеля) | 16 | 0.000 % | −0.127 % |

⚠️ Найбільшу розбіжність має саме **базова** 921600 — третину бюджету приймача
(3.33 %), — і вона працює з нулем помилок CRC. Тобто арифметично перехід на
будь-яку іншу швидкість переліку безпечніший за те, що вже працює.

**Числа перемикання** (їдуть **у пакеті `BAUD`**, а не сидять константами в
мості):

| | Значення | Виведення |
|---|---:|---|
| `BAUD_SWITCH_DELAY_MS` | **100 мс** | обіцянка мосту: «я перемкнусь не пізніше ніж через стільки» |
| `BAUD_REVERT_WINDOW_MS` | **500 мс** | 100 (міст доживає таймер) + 10 (переналаштування порту) + 132 (заміряна затримка задачі моста) ≈ 242 мс, подвоєно свідомо |

**Порядок:** першим перемикається **пульт** — у мить, яку сам контролює (коли
DMA дожував пачку); підтвердження — останній кадр на старій швидкості. У вікні
повернення пульт **мовчить**: почни він пачку, половина її поїхала б на одній
швидкості, половина на іншій.

**Запобіжник:** не почувши осмисленого пакета за 500 мс, пульт сам вертається
на `REMOTE_UI_BAUDRATE` — **завжди додому, ніколи «на попередню»**. Домашня
швидкість це дно, тому вкладених відмов не існує за побудовою. Швидкість
навмисно **не зберігається**: пульт завжди піднімається на 921600.

⚠️ **Практичний наслідок, який треба знати:** після кожного перезапуску стенда
обидва боки зустрічаються на 921 600, і поки клієнт не замовив високу
швидкість, картинка має шви. Перед скаргою «знову рве» перевіряйте
**швидкість**, а не код.

Лічильників відкоту **два**: «пульт не почув моста» і «міст не почув пульта» —
різні події з різними причинами.

## Чого не міряли

Перелік навмисно повний — це місця, де числа **немає**, і його не можна
заповнювати оцінками.

**Пульт:**

- час виконання самого гачка `remoteUiOnFlush` — **не міряно** (оцінка
  «десятки мікросекунд» у `docs/02-architecture.md` розрахункова);
- блокування драйвера на очікуванні кадру LTDC — у `docs/02-architecture.md`
  стоїть «до ~19 мс», але **явного числа в коді EdgeTX немає**: там
  очікування `_frame_addr_reloaded == 0` без тайм-ауту, тобто число виводиться
  з частоти LTDC (60 Гц → ~16.6 мс на кадр), а не заміряне;
- скільки триває найдорожчий прохід задачі транспорту — **не міряно**
  (в коді стоїть оцінка «одиниці мілісекунд»);
- виграш або програш плитки 16×16 проти 32×32 — **не міряно**, дослід не
  проводився.

**Міст:**

- пропускна здатність Wi-Fi при 8.5 дБм — **не міряно**; потужність опущена за
  причиною, якої вже немає (ризик завад радіомодулю знято 25.07);
- три числа `BRINGUP.md` — «чи стартує пульт із конденсатором 1000 мкФ»,
  «напруга на 5 В порту під навантаженням Wi-Fi», «просадка, чи тягне AUX1
  150–250 мА» — **не міряно**: фаза 5 не проводилась, потрібні четвертий дріт
  і трійка конденсаторів, яких фізично немає;
- ESP32-C3 SuperMini: жодне число не перевірене на залізі — плати на руках
  немає; стеля 921600 і буфер 16 КіБ поставлені за аналогією;
- `CONFIG_LWIP_TCP_SND_BUF_DEFAULT` = 32 768 поставлено з міркувань у задачі
  0011 і **відтоді не міряне**.

**Клієнт:**

- зайнятість головного потоку браузера на **телефоні** (розбір + малювання) —
  **не міряно**; для тестового клієнта на tkinter було 3.5 мс на кадр;
- скільки клацань за секунду реально віддає джойстик на телефоні і чи
  вистачає цього, щоб пройти довгий список — **не міряно** (критерій 3.4
  задачі 0022);
- утримання клавіші 10 с без самовільного розтискання — **не міряно**
  (критерій 4.2 задачі 0022).

**Наскрізно:**

- ⚠️ **Затримка «палець → показаний кадр» до і після механізму 0019 —
  не міряна**: наявний на той момент інструмент міряв до дроту, а очікування
  лежить **після** дроту, тобто він непридатний за побудовою. Прилад у клієнті
  з'явився в 0020: медіана **115 мс** проти 463 мс без правила протягу, 90-й
  відсоток ≈**920 мс** — і хвіст належить **пульту**, тому в обох режимах
  однаковий;
- ⚠️ `tools/release_watch.py` має ваду насичення (тример доїжджає до упору й
  перестає рухати канал), через що числа затримки відпускання з задачі 0012
  мають розкид **0…1829 мс** і доказом **не є**;
- повторні передачі TCP як пояснення секундних пауз вводу — **гіпотеза**,
  `tcpdump` не знімався.

# Робоче середовище: Arch Linux

## Найважливіше: DFU не потребує екрана

Режим DFU, яким заливають прошивку, працює, коли пульт підключають до ПК
у **вимкненому** стані. Тобто заливка не вимагає ні екрана, ні меню
завантажувача. Для нашого проєкту це знімає більшу частину страху етапу 0.

Пульт у DFU виглядає як STM32-пристрій `0483:df11`.

## Пакети

```bash
sudo pacman -S dfu-util cmake arm-none-eabi-gcc arm-none-eabi-newlib \
               sdl2 python python-pip git
```

З AUR (`yay`, `paru` — на смак):

```bash
yay -S edgetx-companion      # симулятор + редактор моделей
yay -S edgetx-buddy-bin      # альтернативний заливач прошивки
```

Є ще окремий проєкт **EdgeTX Flasher** із готовими збірками під Linux —
запасний варіант, якщо Companion вередуватиме.

## Правило udev

Без нього `dfu-util` бачитиме пульт, але не зможе писати.

```bash
sudo tee /etc/udev/rules.d/45-stdfu-permissions.rules >/dev/null <<'RULE'
# STM32 DFU (внутрішній завантажувач)
SUBSYSTEMS=="usb", ATTRS{idVendor}=="0483", ATTRS{idProduct}=="df11", MODE:="0666"
RULE
sudo udevadm control --reload-rules && sudo udevadm trigger
```

Варіант суворіший, через групу — на Arch це **`uucp`**, а не `plugdev`:

```bash
sudo usermod -aG uucp $USER   # потім перезайти в систему
```

⚠️ **Пастка, і вона стосується вас напряму.** Companion 2.11.4 сам ставив
правило udev із `MODE:="0666"`, а у 2.12 схема змінилася і права стали
суворішими — саме на 2.12 люди й спотикаються. **Тримайте власне правило**
у `/etc/udev/rules.d/`, не покладайтесь на пакет.

## Перевірка

```bash
# пульт ВИМКНЕНИЙ, підключений по USB
lsusb | grep 0483            # має бути 0483:df11
dfu-util -l                  # має показати альтернативні інтерфейси
```

Якщо порожньо — перевірити кабель (чи він із даними), перевірити, що пульт
саме вимкнений, і чи не тримає пристрій інша програма.

## Доступ до послідовних портів

Перетворювач USB-UART з'явиться як `/dev/ttyUSB0` (CP2102) і теж належить
групі `uucp`:

```bash
groups | grep uucp || sudo usermod -aG uucp $USER
```

## PlatformIO та ESP-IDF

```bash
pip install --user platformio        # або yay -S platformio-core
```

Правила udev для плат ESP32 PlatformIO ставить окремо — див. їхню
документацію, `99-platformio-udev.rules`.

Міст пишеться на **чистому ESP-IDF** (ADR-0004).

### ⚠️ Два можливі власники збірки — обрати один

ESP-IDF може приїхати трьома шляхами одночасно, і вони конфліктують:

1. **Розширення ESP-IDF для VS Code** — тримає свою копію IDF (зазвичай
   `~/esp/`) і свої інструменти (`~/.espressif`).
2. **PlatformIO** — тягне власну копію в `~/.platformio/packages`.
3. **AUR-пакет `esp-idf`** — системний варіант.

Головна пастка: розширення (і скрипт `export.sh`) прописує глобальні
змінні `IDF_PATH` та `IDF_TOOLS_PATH`. Якщо вони «протекли» в оболонку,
збірка PlatformIO почне підхоплювати чужий IDF і ламатися незрозумілим
чином — помилки при цьому виглядають як завгодно, тільки не як конфлікт
середовищ.

### Перевірити перед етапом 2.6

```bash
echo "IDF_PATH=$IDF_PATH"
echo "IDF_TOOLS_PATH=$IDF_TOOLS_PATH"
grep -rn "IDF_PATH\|export.sh" ~/.bashrc ~/.zshrc ~/.profile 2>/dev/null

ls -d ~/esp ~/.espressif ~/.platformio/packages/framework-espidf 2>/dev/null
command -v idf.py && idf.py --version
pacman -Qs esp-idf
code --list-extensions | grep -i espressif
```

Що з цим робити:

- Якщо `IDF_PATH` виставлений глобально — **прибрати з `~/.bashrc`**.
  Правильно активувати середовище точково, у тому терміналі, де збираєш.
- Обрати одного власника збірки і зафіксувати рішення в
  `state/DECISIONS.md`. Змішувати два — гарантований день згаяного часу.

### Що обрати

Обидва варіанти робочі, тож вирішуємо за фактом перевірки:

| | PlatformIO | Розширення ESP-IDF |
|---|---|---|
| Уже описано в проєкті | `platformio.ini` | треба структура IDF |
| Версія IDF | яку дасть платформа, буває стара | будь-яка, керуєш сам |
| `menuconfig` | `pio run -t menuconfig` | графічний, зручніший |
| Дві плати в одному файлі | так, середовища | через профілі, менш зручно |

Оскільки ADR-0004 обрав чистий IDF, розширення виглядає природніше —
особливо через контроль версії й зручний `menuconfig`. Але рішення
відкладене до етапу 2.6: спочатку дивимось, що реально стоїть у системі.

Незалежно від вибору: **логіка моста живе у кількох файлах із тонким
`main`**, щоб переїзд між PlatformIO та `idf.py` коштував годину, а не день.

## Збірка симулятора EdgeTX

Точний перелік залежностей — у документації EdgeTX; вона змінюється, тому
звірятися треба з нею, а не з цим файлом. Орієнтовно потрібні `cmake`,
`qt6-base`, `sdl2`, `libusb`, `python-pyqt6`.

```bash
bash tools/setup-upstream.sh
# далі — за інструкцією EdgeTX для складання симулятора цілі X10
```

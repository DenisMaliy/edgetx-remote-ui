# Архітектура

> Цей документ — про **рішення й підстави**. Покроковий шлях байта від
> малювання в пульті до пікселя в браузері, з числами й вузькими місцями, —
> у `docs/12-pipeline.md`. Він писався за кодом і має перевагу, якщо десь
> розійдуться.

## Загальна схема

```
┌─────────────────────── TX16S (STM32F429) ───────────────────────┐
│                                                                  │
│   LVGL / GUI EdgeTX                                              │
│        │ flushLcd(): область + пікселі + ознака кінця кадру      │
│        ▼                                                         │
│   remote_ui/capture.cpp                                          │
│        ├─► тіньовий кадр 480×272×2 = 261 120 Б  (SDRAM)          │
│        └─► бітова карта брудних плиток 32×32 (без м'ютекса)      │
│                     │                                            │
│   remote_ui/tile.cpp ◄──┘  ріже плитку, кличе rle16              │
│        │                   метод 0 = сирі, 1 = RLE — менший      │
│        ▼                                                         │
│   remote_ui/protocol.cpp        кадрування + CRC16               │
│        │                                                         │
│        ▼                                                         │
│   remote_ui/transport_uart.cpp ──► AUX1 (USART3 + DMA TX)        │
│        ▲                    (власна задача FreeRTOS, пріоритет 2)│
│        │ вхідні команди                                          │
│   remote_ui/input.cpp + input_edgetx.cpp                         │
│        │ підмішує у                                              │
│        ├─► readKeys()          (keys.cpp)                        │
│        ├─► rotaryEncoderGet…() (LvglWrapper.cpp)                 │
│        └─► touchPanelRead()    (LvglWrapper.cpp)                 │
└──────────────────────────────────────────────────────────────────┘
                    │ UART: старт 921600, до 2 625 000 на ходу
┌─────────────────────────────▼────────────────────────────────────┐
│  ESP32 DevKit v1 (C3 SuperMini — кандидат у корпус)              │
│   UART RX (кільцевий буфер) → потоково → WebSocket                │
│   HTTP-сервер: віддає сторінку з **флеша**, вбудовану gzip'ом     │
│   Wi-Fi: точка доступу (AP) або клієнт домашньої мережі          │
└──────────────────────────────────────────────────────────────────┘
                              │ WebSocket
┌─────────────────────────────▼────────────────────────────────────┐
│  Браузер (телефон / ПК)                                          │
│   <canvas> 480×272 ← плитки RGB565 → RGBA                        │
│   pointer events → TOUCH                                         │
│   бокові панелі кнопок → KEY / ENC                               │
└──────────────────────────────────────────────────────────────────┘
```

⚠️ Сторінка **не лежить у файловій системі** моста: файли клієнта
**мініфікуються, потім стискаються gzip'ом** на збірці й вбудовуються в
двійковий файл прошивки (`firmware/esp32/main/CMakeLists.txt`, символи
`_binary_*_gz_start`). Джерело в `webui/` лишається читабельним і з
коментарями українською — оброблений примірник живе тільки в збірці.
`index.html` esbuild не чіпає, лише копіює.

Це важливо для пам'яті, і саме тут початкове правило виявилось хибним:
⚠️ **ціна сторінки в купі моста не дорівнює її розміру на дроті.** Сторінка
вагою 57.8 КБ з'їла 85.2 КБ купи, бо браузер тягне файли кількома
з'єднаннями одночасно, і кожне бере власний буфер (заміряно 2026-08-02,
задача 0022).

## Ключове рішення: беремо змінені області з гачка `flushLcd`

> **Замінює рішення від 2026-07-25** («порівняння двох кадрових буферів»).
> Те рішення спиралося на два твердження про код, і обидва виявилися
> невірними при перевірці за EdgeTX 2.12.2. Розбір — нижче, щоб помилка не
> повторилась.

### Чому старе рішення не працює

Малося на увазі: буферів два, вони чергуються, після свопу маємо новий кадр
і попередній, різниця між ними — і є те, що змінилося.

Що насправді (перевірено за кодом 2.12.2):

1. **`LCD_FIRST/SECOND_FRAME_BUFFER` не містять кадру.** У непрямому режимі
   LVGL малює кожну змінену область у **початок** буфера, щільно, з кроком
   рядка = ширина області, і перемикає буфери після кожного флешу. Там лежить
   останній намальований прямокутник, а не екран.
2. **Пара буферів драйвера завжди однакова.** Справжній кадр — у
   `_LCD_BUF_1`/`_LCD_BUF_2` (`targets/horus/lcd_driver.cpp`), але наприкінці
   кожного циклу драйвер сам копіює всі оновлені області з нового переднього
   в новий задній. Різниця між ними дорівнює нулю **за побудовою**.
3. **Твердження «TX16S у прямому режимі» було перевернуте.** Для TX16S
   визначено `LCD_VERTICAL_INVERT` (`targets/horus/hal.h:826-828`), звідки
   `direct_mode = 0` (`gui/colorlcd/lcd.cpp:129-135`). Ранній вихід за
   `lv_disp_flush_is_last` для цієї цілі **взагалі не компілюється** — тобто
   до гачка доходять **усі** області, а не лише остання. Аргумент проти
   гачка насправді був аргументом за нього.

### Що беремо натомість

Гачок у `flushLcd()` (`gui/colorlcd/lcd.cpp`) — на самому початку функції,
**до** блоку раннього виходу. Звідти ми одночасно отримуємо:

- **прямокутник, що змінився** — тип `rect_t`, це **власний тип EdgeTX**
  (`edgetx_types.h`), а не LVGL; координати логічні, неповернуті;
- **пікселі саме цієї області** — щільно упаковані, крок рядка = ширина
  області;
- **ознаку кінця кадру** — `lv_disp_flush_is_last()`.

Ключове: EdgeTX має **власний** проміжний зворотний виклик між LVGL і
драйвером — `lcdSetFlushCb(void (*)(lv_disp_drv_t*, uint16_t*, const rect_t&))`
(`gui/colorlcd/lcd.h`). Тобто область і пікселі приходять у типах EdgeTX.

### Чим це краще

| | Порівняння буферів | Гачок `flushLcd` |
|---|---|---|
| Працює на TX16S | **ні** (див. вище) | так |
| Пам'ять | +255 КБ на тіньовий кадр | +255 КБ (див. нижче) |
| Процесор | ~522 КБ читань SDRAM на прохід | `memcpy` лише зміненого |
| Залежність від LVGL | нуль… але метод не працює | один виклик + непрозорий вказівник |
| Симулятор = залізо | ні (інший доступ, інша орієнтація) | **так, той самий файл і ті самі дані** |
| Кількість цілей | окремо під кожен драйвер | один файл на всі кольорові цілі |

Про залежність від LVGL чесно: вона лишилась, але звузилася до **однієї
функції** `lv_disp_flush_is_last()` і вказівника, який ми не розіменовуємо.
Ані `lv_area_t`, ані `lv_disp_t`, ані приватні `_lv_refr_*` нам не потрібні —
на відміну від самого драйвера EdgeTX, який до них лізе. Перехід LVGL 8 → 9
зачепить нас у одному рядку.

Найсильніший аргумент — **симулятор і залізо збігаються повністю**: той самий
файл, той самий момент, та сама орієнтація. Крок 1.4 робиться без пульта, і
на залізі не виявиться інакше.

⚠️ **Виправлення за фактом реалізації: рядок «пам'ять» у таблиці був надто
оптимістичний.** «Шлемо одразу» неможливе — гачок працює в `menusTask`, яку
витісняє мікшер, і чекати на місце в буфері передачі він не має права. Тому
`capture.cpp` таки тримає тіньовий кадр 480×272×2 = **261 120 Б** у SDRAM
(`__SDRAM`), а над ним — бітову карту брудних плиток. У внутрішню ОЗП
STM32F429 це не влізло б; наслідок на майбутнє: **кольорова ціль без SDRAM
потребуватиме іншого підходу**.

Виграш гачка від цього не зникає — він в іншому: порівнювати два буфери
неможливо в принципі (див. вище), а тут зміни приносить сам EdgeTX.

### Орієнтація

З цієї точки картинка **логічна, неповернута** — і на залізі, і в симуляторі.
Поворот на 180°, який робить драйвер TX16S (`_copy_rotate_180`), відбувається
**нижче** за нашу точку і нас не стосується. Клієнтові нічого повертати.

### Плитки нікуди не діваються

Сітка плиток лишається — але як одиниця **стиснення й передачі**, а не як
спосіб пошуку змін. Область із гачка ріжеться на плитки, кожна стискається
RLE й ставиться в чергу.

### Де виконується наша робота

Гачок працює в задачі `menusTask` — найнижчий пріоритет, мікшер витісняє її
будь-коли. Тому в самому гачку — **тільки** `memcpy` у наш статичний буфер і
запис прямокутника в чергу. Ніякого DMA2D, ніяких очікувань, ніякого
виділення пам'яті. Стиснення й передача — окремо, поза гачком.

Для масштабу: драйвер у цій самій задачі вже блокується до ~19 мс на очікуванні
кадру LTDC. Наші десятки мікросекунд на цьому фоні — шум.

## Ключове рішення: стиснення RLE, не LZ4

Інтерфейс EdgeTX — великі однотонні площини. RLE по 16-бітних пікселях дає
5–20× майже безкоштовно по процесору. LZ4-кодувальника в дереві EdgeTX немає
(є лише розпакування для шрифтів), тягнути його заради 1.5× зайве.

Формат плитки: `[метод:1][дані]`, метод 0 = сирі пікселі, 1 = RLE.
Кодувальник рахує обидва варіанти й бере менший — гарантія, що стиснення
ніколи не зробить гірше.

## Ключове рішення: ввід через існуючі драйвери

Не намагаємось «натискати кнопки» в GUI. Підмішуємо віртуальний стан у ті самі
місця, звідки читається фізичне залізо. Тоді безкоштовно отримуємо всю логіку
EdgeTX: коротке/довге натискання, автоповтор, прискорення енкодера,
блокування клавіш, звуковий відгук.

Це той самий підхід, яким працює симулятор у EdgeTX Companion.

## Модульність

```
firmware/edgetx-patch/remote_ui/
  remote_ui.h         публічний інтерфейс
  geometry.h          розміри екрана й сітки; TILE_SIDE = 32
  protocol.cpp        кадрування, розбір вхідних команд          [спільне]
  crc16.cpp           контрольна сума кадру                      [спільне]
  capture.cpp         гачок flushLcd, тіньовий кадр, бітова карта
  tile.cpp            нарізка плитки й вибір методу стиснення
  rle16.cpp           кодувальник RLE по 16-бітних пікселях
  hello.cpp           опис пульта клієнтові (клавіші, тримери, сенсор)
  input.cpp           віртуальні клавіші / енкодер / сенсор      [спільне]
  input_edgetx.cpp    підмішування у драйвери EdgeTX
  baudrate.cpp        швидкість на ходу: сходинки й повернення додому
  transport_uart.cpp  залізо: AUX1, власна задача FreeRTOS
  transport_simu.cpp  симулятор: TCP 127.0.0.1:7616
```

⚠️ **Плитка — 32×32, не 16×16.** Число обране умовою «сира плитка має
вміщатись у корисне навантаження разом із заголовком»: 32·32·2 + 9 = 2057 ≤
4096, тоді як 64×64 дало б 8201. На шумі RLE не виграє, і плитка йде сирою —
різати її в момент відправлення нема куди.

⚠️ Чорно-білих цілей у коді поки **немає**: `capture_bw.cpp` не написаний,
підтримка ЧБ-пультів лежить у кроці 1.7, відкладеному рішенням людини.

Специфіки конкретного пульта — нуль рядків. Усе, що відрізняється,
береться з наявних API EdgeTX і передається клієнту в `HELLO`:

```cpp
LCD_W, LCD_H                 // роздільність
sizeof(pixel_t)              // 2 = RGB565, 1 = ЧБ
keysGetSupported()           // маска наявних клавіш
keysGetLabel(EnumKeys)       // людські назви для підписів на екрані
keysGetMaxTrims()            // скільки тримерів
#if defined(HARDWARE_TOUCH)  // чи є сенсор
```

Клієнт малює панель керування динамічно → новий пульт працює без оновлення
застосунку.

## Потік даних і зворотний тиск (backpressure)

Правило: **прошивка ніколи не чекає**. Якщо в буфері передачі немає місця —
плитка позначається брудною і відкладається до наступного кадру. Пропущений
кадр — прийнятно. Заблокований мікшер — ні.

```
if (transportFreeSpace() < needed) { markDirtyAgain(tile); return; }
```

## Транспорти

| | AUX1 (UART) | USB CDC |
|---|---|---|
| Швидкість | старт 921600, стеля **2 625 000** ≈ 262 КБ/с | ~0.5–1 МБ/с |
| DMA на передачу | так (DMA1 Stream3) | треба додати `sendBuffer` |
| USB-C лишається вільним | так | ні |
| Бездротово | так, через ESP32 | ні |
| Основний для MVP | ✅ | другий етап |

Обидва підключаються в одному місці — `serialSetCallBacks()`. Різниця в коді
мінімальна.

⚠️ **921600 — не «мало», а свідомий старт.** Пульт завжди піднімається на
ній, бо на іншому кінці дроту може не бути нікого; високу швидкість замовляє
клієнт на ходу, зі сходинками вниз і поверненням додому за тишею в каналі
([ADR-0005](adr/0005-runtime-baudrate.md), `remote_ui/baudrate.h`). Стеля
2 625 000 — це 42 МГц / 16, тобто **точне** число без похибки дискретизування,
а не округлені «2.5 Мбод».

⚠️ І окремо, щоб не оптимізувати не те: після підняття швидкості вузьким
місцем став **не дріт**, а швидкість малювання самого EdgeTX. Числа — у
`docs/12-pipeline.md`.

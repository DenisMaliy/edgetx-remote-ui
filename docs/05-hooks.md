# Точки дотику з кодом EdgeTX

**Це закритий перелік.** Змінювати файли EdgeTX поза цим переліком не можна
без окремого ADR. Кожен зайвий рядок — це конфлікт при кожному `git rebase`
на нову версію EdgeTX.

Прив'язки перевірені по гілці `main` (стан: липень 2026). Номери рядків
орієнтовні — шукайте по назві функції.

**Стан на 2026-07-26: усі дев'ять пунктів накладені** (задача 0009 закрила
1, 2, 3, 4 і 9). Перелік розширювати не довелося жодного разу; два пункти
навпаки **звужені** за кодом — див. позначки ⚠️ на місці.

## 1. Перелік режимів порту

**`radio/src/dataconstants.h`** (~рядок 249), `enum UartModes`

```cpp
enum UartModes {
  UART_MODE_NONE,
  ...
  UART_MODE_EXT_MODULE,
#if defined(REMOTE_UI)
  UART_MODE_REMOTE_UI,        // ← ДОДАТИ ТУТ, перед COUNT
#endif
  UART_MODE_COUNT SKIP,
  UART_MODE_MAX SKIP = UART_MODE_COUNT-1
};
```

⚠️ Тільки **в кінець**, перед `UART_MODE_COUNT`. Вставка в середину зсуне
значення всіх наступних режимів.

⚠️ `#if defined(REMOTE_UI)` тут обов'язковий, і не для порядку: без нього
`UART_MODE_COUNT` виросло б і в збірці без нашого прапорця, а в меню з'явився б
режим без назви. Саме ця умова робить можливою побайтову ідентичність збірки
без `REMOTE_UI` (задача 0009).

Приємна деталь: у `radio.yml` режими зберігаються **рядками**, а не числами.
Тому навіть якщо upstream колись зсуне нумерацію — конфіги користувачів
не поламаються.

⚠️ Стеля, про яку варто знати: номер режиму зберігається в **чотирьох бітах**
(`SERIAL_CONF_MODE_MASK` у `radio/src/serial.h`, `YAML_ENUM("mode", 4, ...)`).
Наш номер — 11, тобто вільних лишилось чотири. Перевірка стоїть
`static_assert`-ом у `transport_uart.cpp`.

## 2. Назва для YAML

**`radio/src/storage/yaml/yaml_datastructs_funcs.cpp`** (~рядок 2594),
масив `enum_UartModes`

```cpp
#if defined(REMOTE_UI)
  {  UART_MODE_REMOTE_UI, "REMOTE_UI"  },
#endif
```

⚠️ **Одна таблиця, не дві** (виправлено 2026-07-26 за кодом, задача 0009).
Раніше тут було написано додати рядок і в `_old_enum_UartModes` з назвою
`MODE_REMOTE_UI`. Це неправильно: `_old_enum_UartModes` — таблиця
**історичних** назв, її читає лише `r_serialMode()` для успадкованих ключів
`auxSerialMode`/`aux2SerialMode` зі старих `radio.yml`. Наш режим у таких
файлах не міг з'явитися ніколи, а upstream перестав доповнювати цю таблицю ще
на `MODE_LUA`.

Що робить стара прошивка, зустрівши `mode: REMOTE_UI`: `yaml_parse_enum()`
доходить до термінатора `{0, NULL}` і повертає **0**, тобто `UART_MODE_NONE`.
Порт просто вимкнений — плавно, без зіпсованого файлу.

## 3. Прив'язка драйвера

**`radio/src/serial.cpp`**

Включення заголовка (обов'язково з `!defined(BOOT)` — див. нижче):

```cpp
#if defined(REMOTE_UI) && !defined(BOOT)
  #include "remote_ui/remote_ui.h"
#endif
```

`serialSetCallBacks()` — нова гілка **всередині наявного блоку
`#if !defined(BOOT)`**:

```cpp
#if defined(REMOTE_UI)
  case UART_MODE_REMOTE_UI:
    // ctx == nullptr — це від'єднання (порт іде під інший режим).
    remoteUiSetSerialDriver(ctx, drv, port);
    break;
#endif
```

⚠️ **`!defined(BOOT)` не косметика.** Завантажувач збирає той самий
`serial.cpp` і успадковує `-DREMOTE_UI`, але наших джерел не має — без цієї
умови прошивка не злінкується. Та сама пастка, що в гачку 6 (задача 0007).

⚠️ **`port` передається третім аргументом** (додано 2026-07-26, задача 0009).
У переліку було два аргументи, і цього виявилось мало: транспорт мусить сам
відмовитись від будь-якого порту, крім AUX1. Причина — `isSerialModeAvailable()`
з пункту 4 фільтрує лише **меню**, а `initSerialPorts()` бере режим прямо з
`radio.yml` без жодної перевірки. У проєкті, де `radio.yml` правлять наосліп,
рядок `mode: REMOTE_UI` під `AUX2` доїхав би до драйвера без перешкод — а там
`.txDMA = nullptr`, тобто передача пішла б побайтово через чергу на 512 байтів,
яка при переповненні **мовчки викидає** решту пачки (до 4103 байтів). Клієнт
бачив би суцільні помилки CRC, і полагодити через меню було б неможливо.

Умова відмови в `transport_uart.cpp` (`portUsable()`) дослівно повторює пункт 4
нижче. Це свідоме дублювання: там воно ховає режим від людини, тут — від файлу.
**Міняти обидва місця треба разом.**

`serialSetupPort()` — швидкість **і напрямок**, теж усередині наявного
`#if !defined(BOOT)`:

```cpp
#if defined(REMOTE_UI)
  case UART_MODE_REMOTE_UI:
    params.baudrate = REMOTE_UI_BAUDRATE;   // 921600 (ADR-0003)
    params.direction = ETX_Dir_TX_RX;
    break;
#endif
```

⚠️ **Рядок про напрямок доданий 2026-07-26** (задача 0009), у документі його
не було. `serialInit()` заводить `params` з `ETX_Dir_TX`, тобто без нього пульт
говорив би, але **не чув** — і жоден клієнт не зміг би до нього постукати.
Так само робить `UART_MODE_GPS` і `UART_MODE_SPACEMOUSE`, у яких двобічний
обмін.

## 4. Фільтр доступності режиму в меню

**`radio/src/gui/gui_common.cpp`**, функція `isSerialModeAvailable()`

```cpp
#if defined(REMOTE_UI)
#if !defined(AUX_SERIAL_DMA_TX)
  if (mode == UART_MODE_REMOTE_UI) return false;
#else
  if (mode == UART_MODE_REMOTE_UI && port_nr != SP_AUX1) return false;
#endif
#endif
```

⚠️ **Тільки AUX1, без VCP** (звужено 2026-07-26 за кодом, задача 0009).
Раніше тут стояло «AUX1 та VCP». Причина звуження — три властивості драйвера
VCP (`radio/src/targets/common/arm/stm32/usbd_cdc.cpp`):

- `sendBuffer` — `nullptr`, тобто прямого доступу до пам'яті на передачу немає
  взагалі;
- `getByte` — `nullptr`: приймання там будується на `setReceiveCb()`, тобто це
  інший шлях у коді, а не інше значення налаштування;
- `usbSerialPutc()` при переповненні свого кільця **мовчки затирає** те, що в
  ньому лежало, і навіть не перевіряє заповненість.

Тобто на VCP цей транспорт видавав би зіпсовані кадри, а виглядало б це як
доступний режим. Коли USB CDC знадобиться (це другий транспорт із CLAUDE.md),
він отримає власну прив'язку — і разом із нею повернеться в цю умову.

Форма умови повторює наявний `UART_MODE_EXT_MODULE` рядком вище: той теж
живий лише там, де є `AUX_SERIAL_DMA_TX`.

⚠️ **Ця умова продублювана в `transport_uart.cpp` (`portUsable()`), і так
задумано.** Тут вона ховає режим від людини в меню; там — від рядка в
`radio.yml`, який до меню не має жодного стосунку (`initSerialPorts()` фільтру
не викликає). Обидва місця міняються разом.

## 5. Захоплення екрана

**`radio/src/gui/colorlcd/lcd.cpp`**, функція `flushLcd()` (~рядок 72)

⚠️ **Це основний механізм захоплення, а не підказка.** Роль підвищено
2026-07-26: попереднє рішення («порівняння двох кадрових буферів») на TX16S
не працює — розбір у `docs/02-architecture.md`, розділ про захоплення екрана.

Один виклик **на самому початку функції**, до блоку раннього виходу за
`lv_disp_flush_is_last`. Реалізовано в задачі 0005 так:

```cpp
#if defined(REMOTE_UI)
  remoteUiOnFlush(area->x1, area->y1, area->x2, area->y2,
                  (const uint16_t*)color_p, lv_disp_flush_is_last(disp_drv));
#endif
```

Типи LVGL розбираються **на місці виклику**, у чужому файлі. У наш заголовок
не потрапляє ані `lv_area_t`, ані `lv_disp_drv_t` — лише цілі числа й
вказівник. Це навмисно: уся залежність від LVGL живе в патчі, тобто в тих
14 рядках, які й так доведеться переглядати при кожному оновленні EdgeTX.

Чому саме тут, а не в драйвері (`targets/horus/lcd_driver.cpp`): цей файл
спільний для **всіх** кольорових цілей і для симулятора, тож гачок ставиться
один раз. У драйвері довелося б дублювати його в кожну ціль окремо.

Чому **до** раннього виходу: на цілях із прямим режимом (T18, V16, X12S)
блок на рядках ~74-85 відкидає всі області, крім останньої. Гачок після нього
працював би на TX16S і мовчав би на решті.

Що приходить у гачок:

| Параметр | Що це |
|---|---|
| `x1, y1, x2, y2` | межі зміненої області, логічні координати, включно |
| `color_p` | пікселі, RGB565 |
| остання | ознака кінця кадру → час слати `FRAME_END` |

### ⚠️ Розкладка пікселів залежить від цілі — до кроку 1.7 не вирішено

Це єдина відома специфіка, що лишилась у цьому місці, і її треба закрити
перед тим, як збирати симулятор для інших пультів (крок 1.7).

- **Непрямий режим** (`direct_mode = 0`, наш TX16S і всі цілі з
  `LCD_VERTICAL_INVERT`): LVGL малює область у початок свого буфера
  **щільно**, крок рядка дорівнює ширині області. Саме на це розраховує
  чинний код захоплення.
- **Прямий режим** (T18, V16, X12S): LVGL малює прямо в повноекранний буфер.
  Крок рядка — `LCD_W`, а не ширина області, і пікселі треба брати зі
  зсувом. Чинний код прочитав би там сміття.

Що з цим робити (рішення прийняте, реалізація — у задачі кроку 1.7):
гачок отримує **додатковий параметр — крок рядка в пікселях**, обчислений на
місці виклику. Так специфіка лишається в патчі, а наш код працює з обома
розкладками однаково.

⚠️ **Не вгадувати**: перед реалізацією перевірити за кодом LVGL, куди саме
вказує `color_p` у прямому режимі — на початок буфера чи на перший піксель
області. Від цього залежить, чи потрібен ще й зсув. Припущення тут коштує
мовчазно зіпсованої картинки на чужому пульті.

Усередині гачка — **тільки** копіювання в наш статичний буфер і запис
прямокутника в чергу. Виконується в задачі `menusTask` (найнижчий пріоритет),
тому: жодного DMA2D, жодних очікувань, жодного виділення пам'яті. Стиснення,
кадрування й передача — поза гачком.

## 6. Емуляція клавіш

**`radio/src/keys.cpp`**, функція `keysPollingCycle()` (~рядок 476)

```cpp
  uint32_t keys_input = readKeys();
#if defined(REMOTE_UI) && !defined(BOOT)
  keys_input |= remoteUiGetKeys();
  trims_input |= remoteUiGetTrims();     // після рядка з READ_TRIMS
#endif
```

Так ми отримуємо всю логіку EdgeTX безкоштовно: коротке й довге натискання,
автоповтор, блокування клавіш.

⚠️ **Саме `|=`, ніколи `=`.** Емульований ввід **додається** до фізичного.
Фізичні клавіші пульта мають працювати завжди, хоч би що робив клієнт і чи він
узагалі живий. Це межа, за яку заходити не можна.

⚠️ **`&& !defined(BOOT)` обов'язкове** (уточнено 2026-07-26, задача 0007):
завантажувач збирає той самий `keys.cpp` і успадковує `-DREMOTE_UI`, але наших
джерел не має. Без цієї умови прошивка не злінкується на етапі 2.

## 7. Емуляція енкодера й сенсора

**`radio/src/gui/colorlcd/LvglWrapper.cpp`**

У `rotaryDriverRead()` (~рядок 255):

```cpp
  rotenc_t newPos = rotaryEncoderGetValue();
#if defined(REMOTE_UI)
  newPos += remoteUiGetEncoderOffset();
#endif
```

⚠️ **`Offset`, а не `Delta`** (уточнено 2026-07-26). Назовні йде **накопичена
позиція**, а не приріст. EdgeTX сам рахує різницю з попереднім читанням і
запам'ятовує суму; віддавши раз «+3» і потім нуль, ми породили б фантомний
оберт назад. Тому накопичувач не обнуляється навіть при розриві.

Другий рядок — прискорення (задача 0008):

```cpp
  remoteUiAddEncoderDt(&rotencDt);
```

⚠️ **Вказівник, а не `rotencDt += remoteUiTakeEncoderDt()`** (уточнено
2026-07-26 за кодом). `rotencDt` пише ще й переривання енкодера, а
«прочитати-додати-записати» з задачі не атомарне. З вказівником наша функція
може **не робити запису зовсім**, поки віддалених клацань немає, — і тоді без
клієнта фізична ручка поводиться точно так само, як до Remote UI. Рядок у
чужому файлі однаково один.

Навіщо цей рядок узагалі: `rotencDt` — накопичувач проміжків між клацаннями
(`rotary_encoder_driver.cpp` робить `+= dt` у перериванні, `LvglWrapper.cpp`
бере різницю). Наш шлях його не рухає, тому `dt` завжди нульове, EdgeTX вважає,
що ручку крутять нескінченно швидко, і прискорення застигає на максимумі —
виставити значення «на кілька одиниць» стає неможливо.

⚠️ **Залишковий ризик, прийнятий свідомо:** `*rotencDt += pending` не атомарне.
Переривання, що влучить у вікно в три інструкції, втратить свій інкремент.
Наслідок обмежений **одним фізичним клацанням із завищеним прискоренням**;
положення й напрямок не зачіпаються, а саме вікно відкривається лише тоді, коли
щойно прийшло віддалене клацання. Прибрати повністю можна тільки критичною
секцією, тобто виходом за один дозволений рядок. Ціна визнана невиправданою
(підтверджено асистентом 2026-07-26); рішення відкрите до перегляду, якщо на
залізі виявиться інакше.

У `touchDriverRead()` (~рядок 180): перед читанням фізичного сенсора
перевірити чергу віддалених подій:

```cpp
#if defined(REMOTE_UI)
  {
    int16_t rx, ry;
    bool rpressed;
    if (remoteUiPopTouch(&rx, &ry, &rpressed)) {
      data->point.x = rx;
      data->point.y = ry;
      data->state = rpressed ? LV_INDEV_STATE_PRESSED : LV_INDEV_STATE_RELEASED;
      reset_inactivity();
      return;
    }
  }
#endif
```

⚠️ **Три вказівники, а не `lv_indev_data_t*`** (уточнено 2026-07-26). Прийняти
структуру LVGL означало б затягти LVGL у наш заголовок, а рішення від того ж
дня каже протилежне: типи LVGL розбираються **на місці виклику**. Ціна —
13 рядків у чужому файлі замість трьох. Ціна свідома.

⚠️ Зверніть увагу на умову `if (!isBacklightEnabled())` у цій функції —
вона глушить сенсор при вимкненій підсвітці. Тому гачок ставиться **до** неї
і до `touchPanelEventOccured()`, інакше застосунок не «розбудить» пульт.

## 9. Переклади

**`radio/src/translations/translation_def.h`** (~рядок 132)

Рядок назви режиму в масиві `STR_AUX_SERIAL_MODES`. Мінімум — англійська.

```cpp
#if defined(REMOTE_UI)
#define TR_AUX_SERIAL_MODES_12      "Remote UI"
#define TR_AUX_SERIAL_MODES         SA12(TR_AUX_SERIAL_MODES)
#else
#define TR_AUX_SERIAL_MODES         SA11(TR_AUX_SERIAL_MODES)
#endif
```

⚠️ **Один файл, а не двадцять** — і це варто пояснити, бо очевидний шлях тут
неправильний. `TR_AUX_SERIAL_MODES` — це макрос **фіксованої арності**
(`SA11` = рівно одинадцять елементів), а самі рядки `TR_AUX_SERIAL_MODES_1…11`
визначені в кожному з **19** мовних файлів `radio/src/translations/i18n/*.h`
окремо. Додавати дванадцятий рядок туди означало б 19 змінених чужих файлів
замість одного.

Виходить дешевше, бо `translation_def.h` включається **перед** мовним файлом, а
макрос розкривається пізніше — у місці використання (`STRARRAY` у
`translations.cpp` і в кожному `translations/sim/lang_*.cpp`). Тому рядок,
визначений тут, доступний усім мовам, і жодна з них його не перекриває.

Спостереження в upstream, нас не зачіпає: у цьому масиві **переплутані місцями
підписи 4 і 5**. У переліку `UartModes` четвертий — `SBUS_TRAINER`, п'ятий —
`SBUS_TRAINER_INV`, а рядки `TR_AUX_SERIAL_MODES_4/5` кажуть навпаки
(«SBUS Trn Inv.» і «SBUS Trainer»), і однаково в усіх 19 мовах. Кандидат в
окремий PR у EdgeTX.

## Як тримати це в порядку

```
commit A: нові файли        ← при rebase не конфліктує ніколи
commit B: ці 88 рядків      ← при rebase конфліктує рідко і дрібно
```

`/rebase-check` перевіряє гілку на свіжому upstream і повідомляє, якщо
щось із цього переліку зсунулось.

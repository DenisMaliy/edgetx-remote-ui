# Точки дотику з кодом EdgeTX

**Це закритий перелік.** Змінювати файли EdgeTX поза цим переліком не можна
без окремого ADR. Кожен зайвий рядок — це конфлікт при кожному `git rebase`
на нову версію EdgeTX.

Прив'язки перевірені по гілці `main` (стан: липень 2026). Номери рядків
орієнтовні — шукайте по назві функції.

## 1. Перелік режимів порту

**`radio/src/dataconstants.h`** (~рядок 249), `enum UartModes`

```cpp
enum UartModes {
  UART_MODE_NONE,
  ...
  UART_MODE_EXT_MODULE,
  UART_MODE_REMOTE_UI,        // ← ДОДАТИ ТУТ, перед COUNT
  UART_MODE_COUNT SKIP,
  UART_MODE_MAX SKIP = UART_MODE_COUNT-1
};
```

⚠️ Тільки **в кінець**, перед `UART_MODE_COUNT`. Вставка в середину зсуне
значення всіх наступних режимів.

Приємна деталь: у `radio.yml` режими зберігаються **рядками**, а не числами.
Тому навіть якщо upstream колись зсуне нумерацію — конфіги користувачів
не поламаються.

## 5. Захоплення екрана

**`radio/src/gui/colorlcd/lcd.cpp`**, функція `flushLcd()` (~рядок 72)

⚠️ **Це основний механізм захоплення, а не підказка.** Роль підвищено
2026-07-26: попереднє рішення («порівняння двох кадрових буферів») на TX16S
не працює — розбір у `docs/02-architecture.md`, розділ про захоплення екрана.

Один виклик **на самому початку функції**, до блоку раннього виходу за
`lv_disp_flush_is_last`. Реалізовано в задачі 0005 так:

```cpp
#if defined(REMOTE_UI)
  remoteUiOnFlush(area->x1, area->y1, area->x2, area->y2,
                  (const uint16_t*)color_p, lv_disp_flush_is_last(disp_drv));
#endif
```

Типи LVGL розбираються **на місці виклику**, у чужому файлі. У наш заголовок
не потрапляє ані `lv_area_t`, ані `lv_disp_drv_t` — лише цілі числа й
вказівник. Це навмисно: уся залежність від LVGL живе в патчі, тобто в тих
14 рядках, які й так доведеться переглядати при кожному оновленні EdgeTX.

Чому саме тут, а не в драйвері (`targets/horus/lcd_driver.cpp`): цей файл
спільний для **всіх** кольорових цілей і для симулятора, тож гачок ставиться
один раз. У драйвері довелося б дублювати його в кожну ціль окремо.

Чому **до** раннього виходу: на цілях із прямим режимом (T18, V16, X12S)
блок на рядках ~74-85 відкидає всі області, крім останньої. Гачок після нього
працював би на TX16S і мовчав би на решті.

Що приходить у гачок:

| Параметр | Що це |
|---|---|
| `x1, y1, x2, y2` | межі зміненої області, логічні координати, включно |
| `color_p` | пікселі, RGB565 |
| остання | ознака кінця кадру → час слати `FRAME_END` |

### ⚠️ Розкладка пікселів залежить від цілі — до кроку 1.7 не вирішено

Це єдина відома специфіка, що лишилась у цьому місці, і її треба закрити
перед тим, як збирати симулятор для інших пультів (крок 1.7).

- **Непрямий режим** (`direct_mode = 0`, наш TX16S і всі цілі з
  `LCD_VERTICAL_INVERT`): LVGL малює область у початок свого буфера
  **щільно**, крок рядка дорівнює ширині області. Саме на це розраховує
  чинний код захоплення.
- **Прямий режим** (T18, V16, X12S): LVGL малює прямо в повноекранний буфер.
  Крок рядка — `LCD_W`, а не ширина області, і пікселі треба брати зі
  зсувом. Чинний код прочитав би там сміття.

Що з цим робити (рішення прийняте, реалізація — у задачі кроку 1.7):
гачок отримує **додатковий параметр — крок рядка в пікселях**, обчислений на
місці виклику. Так специфіка лишається в патчі, а наш код працює з обома
розкладками однаково.

⚠️ **Не вгадувати**: перед реалізацією перевірити за кодом LVGL, куди саме
вказує `color_p` у прямому режимі — на початок буфера чи на перший піксель
області. Від цього залежить, чи потрібен ще й зсув. Припущення тут коштує
мовчазно зіпсованої картинки на чужому пульті.

Усередині гачка — **тільки** копіювання в наш статичний буфер і запис
прямокутника в чергу. Виконується в задачі `menusTask` (найнижчий пріоритет),
тому: жодного DMA2D, жодних очікувань, жодного виділення пам'яті. Стиснення,
кадрування й передача — поза гачком.

## 6. Емуляція клавіш

**`radio/src/keys.cpp`**, функція `keysPollingCycle()` (~рядок 476)

```cpp
  uint32_t keys_input = readKeys();
#if defined(REMOTE_UI) && !defined(BOOT)
  keys_input |= remoteUiGetKeys();
  trims_input |= remoteUiGetTrims();     // після рядка з READ_TRIMS
#endif
```

Так ми отримуємо всю логіку EdgeTX безкоштовно: коротке й довге натискання,
автоповтор, блокування клавіш.

⚠️ **Саме `|=`, ніколи `=`.** Емульований ввід **додається** до фізичного.
Фізичні клавіші пульта мають працювати завжди, хоч би що робив клієнт і чи він
узагалі живий. Це межа, за яку заходити не можна.

⚠️ **`&& !defined(BOOT)` обов'язкове** (уточнено 2026-07-26, задача 0007):
завантажувач збирає той самий `keys.cpp` і успадковує `-DREMOTE_UI`, але наших
джерел не має. Без цієї умови прошивка не злінкується на етапі 2.

## 7. Емуляція енкодера й сенсора

**`radio/src/gui/colorlcd/LvglWrapper.cpp`**

У `rotaryDriverRead()` (~рядок 255):

```cpp
  rotenc_t newPos = rotaryEncoderGetValue();
#if defined(REMOTE_UI)
  newPos += remoteUiGetEncoderOffset();
#endif
```

⚠️ **`Offset`, а не `Delta`** (уточнено 2026-07-26). Назовні йде **накопичена
позиція**, а не приріст. EdgeTX сам рахує різницю з попереднім читанням і
запам'ятовує суму; віддавши раз «+3» і потім нуль, ми породили б фантомний
оберт назад. Тому накопичувач не обнуляється навіть при розриві.

⚠️ **Дозволений другий рядок у цьому ж гачку** (рішення від 2026-07-26,
реалізація — задача 0008): оновлювати позначку часу останнього клацання
енкодера часом приходу пакета `ENC`. Без цього `dt` завжди нульове, EdgeTX
вважає, що ручку крутять нескінченно швидко, і прискорення застигає на
максимумі — виставити значення «на кілька одиниць» стає неможливо.

У `touchDriverRead()` (~рядок 180): перед читанням фізичного сенсора
перевірити чергу віддалених подій:

```cpp
#if defined(REMOTE_UI)
  {
    int16_t rx, ry;
    bool rpressed;
    if (remoteUiPopTouch(&rx, &ry, &rpressed)) {
      data->point.x = rx;
      data->point.y = ry;
      data->state = rpressed ? LV_INDEV_STATE_PRESSED : LV_INDEV_STATE_RELEASED;
      reset_inactivity();
      return;
    }
  }
#endif
```

⚠️ **Три вказівники, а не `lv_indev_data_t*`** (уточнено 2026-07-26). Прийняти
структуру LVGL означало б затягти LVGL у наш заголовок, а рішення від того ж
дня каже протилежне: типи LVGL розбираються **на місці виклику**. Ціна —
13 рядків у чужому файлі замість трьох. Ціна свідома.

⚠️ Зверніть увагу на умову `if (!isBacklightEnabled())` у цій функції —
вона глушить сенсор при вимкненій підсвітці. Тому гачок ставиться **до** неї
і до `touchPanelEventOccured()`, інакше застосунок не «розбудить» пульт.

## Як тримати це в порядку

```
commit A: нові файли        ← при rebase не конфліктує ніколи
commit B: ці 34 рядки       ← при rebase конфліктує рідко і дрібно
```

`/rebase-check` перевіряє гілку на свіжому upstream і повідомляє, якщо
щось із цього переліку зсунулось.

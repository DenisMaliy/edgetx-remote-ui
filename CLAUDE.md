# TX16S Remote UI — контекст проєкту

> Цей файл читає кожна сесія Claude Code. Тримай його коротким і актуальним.
> Детальні документи — у `docs/`. Поточний стан роботи — у `state/PROGRESS.md`.

## Що робимо

Заміна фізично розбитого екрана RadioMaster TX16S на смартфон/браузер.
Прошивка EdgeTX віддає **справжній кадровий буфер** назовні і приймає назад
**емульований ввід** (сенсор, клавіші, енкодер). Клієнт нічого не знає про
внутрішню логіку EdgeTX — він показує пікселі й шле натискання.

Наслідок: працює **все** без винятку — системне меню, налаштування моделі,
меню Lua-скриптів (ELRS-конфігуратор тощо), майстри, спливні вікна.

## Короткострокова ціль (MVP)

1. Зображення екрана пульта на смартфоні.
2. Обробка натискань — емуляція сенсорного екрана.
3. Бокові панелі з дублюванням фізичних клавіш і енкодера.

## Довгострокова ціль

Підтримка більшості пультів на EdgeTX (кольорові й ЧБ) і, за можливості,
прийняття у upstream EdgeTX під окремим прапорцем збірки.

## Залізо

- Пульт: RadioMaster TX16S, STM32F429, екран 480×272 RGB565, ціль збірки `X10`/`RADIO_TX16S`.
- Прошивка на пульті: **EdgeTX 2.12.x**. Наша гілка базується на релізній
  гілці **2.12**, не на `main` — вміст SD-картки прив'язаний до версії, і
  збірка від `main` (2.13-dev) викличе попередження про невідповідність
  картки. `main` перевіряємо тільки командою `/rebase-check`.
- Транспорт: **AUX1** (зовнішній 4-пін роз'єм знизу: GND / 5V / TX / RX).
  Саме AUX1, бо в нього є DMA на передачу. Деталі — `docs/06-hardware.md`.
- Міст: ESP32 DevKit v1 для розробки, C3 SuperMini — кандидат у корпус (ADR-0003).
- Середовище моста: **чистий ESP-IDF, збирач `idf.py`** (ADR-0004 + доповнення
  2026-07-26). Не PlatformIO: там стоїть лише Arduino, і він дотягнув би третю
  копію IDF, до того ж старішу за наявну 5.5.4.
- Швидкість каналу: **921600** бод.
- Другий транспорт: USB CDC (той самий протокол, інша прив'язка драйвера).

## ⚠️ Головне обмеження проєкту

**Екран пульта не працює.** Жодна інструкція виду «зайди в меню і вибери»
не застосовна. Будь-яка зміна налаштувань пульта на етапах 0–2 робиться
**наосліп**: через режим завантажувача (bootloader) пульт стає USB-накопичувачем,
і файли `RADIO/radio.yml` та `MODELS/*.yml` редагуються з ПК.

Якщо агент пропонує крок «відкрий налаштування на пульті» — це помилка,
крок треба переписати.

## Дві сесії: асистент і команда

Проєкт ведеться у **двох окремих сесіях Claude Code** в одному репозиторії.

- **Асистент** — розмова з людиною, рішення, задачі, рецензії. Коду не пише.
  Запуск: `/assistant`. Опис ролі — `docs/ROLE-assistant.md`.
- **Команда** — власне робота. Запуск: `/catchup`.

Міст між ними — файли задач у `tasks/`, а не копіпаст:

```
асистент ──► tasks/NNNN.md   Мета / Критерії / Обмеження
команда  ──► tasks/NNNN.md   Результат
асистент ──► tasks/NNNN.md   Рецензія (за доказами з репозиторію)
```

**Один артефакт — один автор.** Повна таблиця власності в
`docs/ROLE-assistant.md`. Коротко: асистент володіє `docs/` і `tasks/`
(крім розділу «Результат»); команда володіє кодом, `PROGRESS.md` і
`handoffs/`.

Дрібниці йдуть повз міст без оформлення — перелік у `tasks/INDEX.md`.

### Правило вказівника: у повідомленні — адреса, у файлі — зміст

⚠️ **Людина не поштар.** Вона не має переносити між сесіями абзаци тексту, і
жодне рішення не має існувати тільки в повідомленні.

Обидві сесії пишуть людині **коротко й вказівником**:

```
Промпт для команди: візьми tasks/0018-bridge-losses.md, критерії 1 і 2.
Промпт для асистента: подивись розділ «Результат» tasks/0018, потрібне
                      рішення щодо розміру пачки.
```

Усе, що має пережити сьогоднішній день, пишеться **у файл** — у задачу, у
рецензію, у `state/DECISIONS.md` — і **потім** називається адреса. Якщо
рішення виявилось тільки в промпті, воно втрачене: наступна сесія його не
побачить.

Дозволено додати в повідомлення один-два рядки про те, **з чого почати** і
**чого не робити**, якщо це не записано у файлі. Усе інше — у файл.

### Життя сесії: коли закривати й відкривати

Сесія не вічна: контекст заповнюється, і сесія починає гірше пам'ятати
власний початок. Тому робота ріжеться на сесії свідомо, а не тоді, коли
стало погано.

**Закривати сесію варто:**

- після того, як задачу **прийнято** рецензією;
- перед фізично незворотним кроком (прошивання наосліп, перше підключення) —
  свіжий контекст помиляється рідше;
- коли сесія вже провела **дві-три задачі** поспіль.

**Порядок незмінний:**

```
кінець сесії  →  /handoff   (команда фіксує зроблене й наступні кроки)
нова сесія    →  /catchup   (піднімає стан, останній handoff, git)
```

⚠️ **Називати цей момент — обов'язок асистента.** Людина не має вгадувати,
коли сесія «втомилась»: асистент сам каже «тут закриваємо, зроби handoff,
далі нова сесія з catchup». Не сказав — вважай, що забув.

## Структура репозиторію

```
docs/           ТЗ, архітектура, протокол, план, точки дотику, залізо
tasks/          Міст асистент ↔ команда: одна задача — один файл
state/          Живий стан: PROGRESS.md, DECISIONS.md, ASSISTANT.md, handoffs/
firmware/edgetx-patch/   Наш код для EdgeTX (нові файли + патчі гачків)
firmware/esp32/          Прошивка моста
webui/                   Клієнт (браузер)
tools/                   Скрипти збірки, тестовий клієнт, перевірка rebase
upstream/edgetx/         Клон EdgeTX (НЕ в git, ставиться tools/setup-upstream.sh)
```

## Правила роботи з кодом EdgeTX

Це найважливіше правило проєкту. Порушення = біль при кожному оновленні EdgeTX.

1. **Нові файли — вільно. Чужі файли — по краплині.**
   Повний дозволений перелік місць у коді EdgeTX — `docs/05-hooks.md`.
   Хочеш змінити щось поза цим переліком — спочатку ADR, потім код.
2. **Два коміти.** Комміт A = тільки нові файли. Комміт B = тільки гачки.
   Так `git rebase` на новий upstream конфліктує максимум у десятку рядків.
3. **Ніякої залежності від LVGL API там, де можна її уникнути.**
   Захоплення екрана робимо порівнянням двох кадрових буферів, а не гачком
   на `flush_cb`. LVGL 8 → 9 зламає flush; порівняння буферів переживе.
4. **Усе під прапорцем збірки `REMOTE_UI`.** Флеш на F4-цілях майже вичерпаний.
5. **Специфіка конкретного пульта в коді — нуль рядків.** Роздільність,
   набір клавіш, наявність сенсора віддаються клієнту в пакеті `HELLO`
   через наявні API (`keysGetSupported`, `keysGetLabel`, `LCD_W/LCD_H`).

## Команди

- `/assistant` — увійти в роль асистента (окрема сесія).
- `/task-new <тема>` — асистент створює задачу.
- `/task-report <N>` — команда записує результат.
- `/task-review <N>` — асистент рецензує за доказами.
- `/catchup` — на початку сесії команди: стан, останній handoff, git.
- `/handoff` — наприкінці сесії: зафіксувати зроблене, рішення, наступні кроки.
- `/build <target>` — зібрати прошивку або симулятор.
- `/rebase-check` — перевірити гілку на свіжому upstream EdgeTX.
- `/adr <тема>` — оформити архітектурне рішення.

## Мова проєкту

**Українською:**
- спілкування з людиною;
- коментарі в коді (усі, включно з `//` і doxygen);
- повідомлення комітів;
- документація, ADR, handoff-и, журнал рішень;
- рядки логів і повідомлення про помилки, які бачить людина.

**Англійською лишаються** (це не переклад, а частина коду):
- назви змінних, функцій, файлів, типів, констант;
- назви пакетів протоколу (`HELLO`, `TILE`, `TOUCH`);
- назви гілок git і префікси комітів (`feat:`, `fix:`);
- усе, що приходить із EdgeTX або ESP-IDF.

**Між собою агенти можуть спілкуватися як завгодно.** Мовна вимога
стосується того, що потрапляє в репозиторій або до людини, а не внутрішніх
міркувань і проміжних повідомлень між агентами.

Простими словами; англомовний термін — українською, у дужках англійською
при першій згадці.

### Формат комітів

Conventional Commits із українським описом:

```
feat: захоплення кадру порівнянням буферів
fix: втрата плитки при переповненні буфера передачі
docs: уточнено розпіновку AUX1
refactor: винесено RLE в окремий файл
chore: оновлено upstream EdgeTX
```

Тіло коміту — теж українською, якщо воно потрібне.

### ⚠️ Виняток на майбутнє

Якщо дійде до PR у upstream EdgeTX (етап 5.5), туди йде **англійська**:
коментарі в коді, повідомлення комітів, опис PR. Це вимога чужого проєкту,
не наша. Переклад робиться окремою задачею перед подачею PR — див.
`docs/04-plan.md`, пункт 5.5.
